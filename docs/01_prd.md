## Q1. 누가 쓸까?

**학교·시청·공공기관 홈페이지에서 필요한 메뉴를 찾는 데 시간이 오래 걸리는, 웹에 익숙하지 않은 성인.**

- **대표 사용자 (확정):** 개발자의 할머니 같은 고령 사용자. 시청 홈페이지에서 여권 신청 안내를 찾아야 하는데, 배너·뉴스·행사·SNS가 섞인 첫 화면에서 어디를 눌러야 할지 몰라 여러 메뉴를 열어 본다.
- **두 번째 사용자:** 개발자의 어머니처럼 예전에는 잘 찾았지만 요즘 버튼이 작아서 찾기 힘들어진 중년 사용자. 웹을 몰라서가 아니라 **보기가 어려워져서** 막힌다.
- **돈을 낼 쪽 (D2 결정: 기관 실증):** 대학·지자체·공공기관. 개인용 확장은 효과를 증명하는 도구이고, 사업은 기관 실증으로 검증한다. **기관 담당자 인터뷰는 아직 0건** → [03](03_user_research.md) U4

> 근거 수준: 두 사용자는 개발자가 가족에게서 들은 이야기입니다(2026-10-31 진술). 아직 EasyWeb을 보여 주고 관찰한 기록은 0건입니다. 관찰은 가능하다고 확인했습니다(D3) → [03](03_user_research.md) U2

## Q2. 뭐가 답답한가?

1. **찾는 것 자체가 어렵다.** 첫 화면에 로그인·조회·신청 같은 실제 업무 메뉴와 홍보 배너·뉴스·행사·SNS가 함께 있어서, 글씨를 키워도 "무엇을 눌러야 하는지"가 보이지 않는다.
2. **버튼이 작아서 보이지 않는다.** 예전에는 잘 찾던 사람도 시력이 떨어지면서 작은 메뉴 글씨와 버튼 때문에 힘들어한다 (어머니 진술). 화면 전체를 확대하면 메뉴가 화면 밖으로 밀려 오히려 찾기 어려워질 수 있다 (확인 필요).
3. **사이트마다 구조가 다르다.** 대학·시청·정부·공공기관·도서관이 메뉴 이름과 위치가 다 달라서, 한 사이트에서 익힌 방법이 다른 사이트에서 통하지 않는다.
4. **기존 접근성 도구는 문제를 알려줄 뿐이다.** 검사 도구는 접근성 문제를 찾아 주지만, 사용자에게 "지금 무엇을 누르면 되는지"를 보여 주지는 않는다. (지원서 Q2 · 02 벤치마킹에서 확인 필요)

## Q3. 어떻게 풀까?

**웹에 익숙하지 않은 사람이 기관 홈페이지를 쓸 수 있도록, 지금 보고 있는 페이지에서 실제로 있는 주요 기능을 찾아 큰 버튼 6개로 다시 보여 주는 Chrome 확장이에요.**

사이트를 새로 만들지 않습니다. 원래 사이트는 그대로 두고, 로그인·인증·신청은 원래 화면에서 진행합니다.

## Q4. 기능 딱 3개?

1. **주요 기능 찾기:** 확장 버튼을 누르면 현재 페이지의 보이는 링크·버튼·검색창을 읽고, 로그인 · 검색 · 공지사항 · 학사정보 · 신청·조회 · 이용 안내 6개 분류로 나눈다. 실제로 있는 것만 보여 주고 없는 기능은 만들지 않는다. 판단은 규칙 기반이며 근거(이름·위치·주변 제목·본문 관계)가 있는 것만 채택한다.
2. **쉬운 화면:** 처음에는 **최대 6개**를 큰 카드로 보여 주고, 필요하면 **「다른 기능 보기 →」 / 「← 이전 기능」**으로 더 본다 (사용자 확정 정책, 2026-10-31 이름 변경). 「다른 기능 보기」와 「다시 찾기」는 카드 바로 위에 큰 버튼으로 둔다. 큰 글씨, 키보드 조작, 스크린리더 안내, 좁은 화면 재배치를 지원한다. Esc나 「원본 화면 보기」로 언제든 원래 화면으로 돌아간다.
3. **원본과 안전하게 연결:** 일반 링크는 바로 이동한다. JavaScript 버튼·팝업·다운로드·로그인(SSO)·같은 페이지 안 이동은 **원본 위치를 표시**하고 사용자가 직접 누르게 한다. 원본이 바뀌었으면 낡은 카드를 막고 「다시 찾기」를 안내한다.

**가능하면 :** 기관 담당자가 중요 메뉴를 직접 지정하는 기관용 설정 (지원서 2단계), 기관 홈페이지에 바로 넣는 웹 모듈·SDK

**안 할 것 :** 로그인·결제·신청·삭제를 대신 실행, 입력한 내용 읽기, 분석 결과를 서버로 보내기, 모든 웹사이트 지원 약속, 모바일 Chrome, 브라우저 내부 페이지, AI 분류의 기본 탑재. 단, 우리 검토 자료로 학습한 작은 순위 모델이 엔진이 이미 찾은 안전한 후보의 순서만 정하는 **실험 빌드**는 만든다(기본 꺼짐, 확장 안 정적 파일, 외부 호출 없음, 엔진이 유형을 못 정한 일반 페이지에서만, 2026-11-19 사용자 지시 → [09](09_local_ai_review.md) 12·13절)

## Q5. 어떻게 생겼나?

**한 화면 (원본 페이지 위에 덮는 쉬운 화면)** — 자세한 구성은 [06 화면](06_screens.md)

- 위: EasyWeb 이름, 「원본 화면 보기」 버튼
- 가운데 머리: 지금 보고 있는 사이트 주소, **「자주 쓰는 버튼」 줄**(처음 화면 · 로그인 · 회원가입 중 페이지에 실제로 있는 것), "무엇을 하시겠어요?", 설명 한 줄
- 처음 화면·로그인·회원가입은 모든 페이지에 있지만 **홈에서만 핵심 기능**이다. 홈이 아닌 페이지에서는 카드 6개에서 빼서 「자주 쓰는 버튼」 줄에 두고, 홈에서는 로그인을 카드로 둔다 (2026-10-31 사용자 결정)
- 본문: 「바로 이용하기」 아래 카드 최대 6개 (아이콘 · 분류 이름 · 설명 · 찾은 메뉴 이름 · 연결된 사이트/새 창 안내 · 「원본 페이지로 이동」 또는 「원본에서 계속하기」), 카드 바로 위 오른쪽에 큰 버튼 「↻ 다시 찾기」·「다른 기능 보기 →」와 "N번째 화면" 표시
- 아래: 「← 이전 기능 / 다른 기능 보기 →」, "로그인·인증·신청은 원래 사이트에서 진행해요."
- 상태 화면: 기능을 못 찾음 · 원본이 바뀜 · 원본 위치 안내 성공/실패

## ★ 한 단락 PRD

EasyWeb은 학교·시청·공공기관 홈페이지에서 필요한 메뉴를 찾기 어려운 고령 사용자와, 시력이 떨어져 작은 버튼을 찾기 힘들어진 중년 사용자를 위한 Chrome 확장이다. 지금 기관 홈페이지는 업무 메뉴와 배너·뉴스·행사가 한 화면에 섞여 있고, 버튼은 작고, 사이트마다 구조가 달라 무엇을 눌러야 할지 알기 어렵다. 핵심 기능은 3가지다. 첫째, 사용자가 확장 버튼을 누르면 현재 페이지의 보이는 링크·버튼·검색창을 읽어 로그인·검색·공지사항·학사정보·신청·조회·이용 안내로 나누고, 근거가 있는 실제 기능만 고른다. 둘째, 처음에는 최대 6개를 큰 카드로 보여 주고 카드 위의 큰 「다른 기능 보기」 버튼으로 더 볼 수 있게 하며, 키보드·스크린리더·확대에서도 쓸 수 있고 Esc로 언제든 원본에 돌아간다. 셋째, 일반 링크는 바로 이동하고 스크립트·팝업·다운로드·인증 제어는 원본 위치만 표시해 사용자가 직접 누르게 하며, 원본이 바뀌면 낡은 카드를 막는다. 입력 내용은 읽지 않고, 분석 결과를 외부로 보내지 않으며, 로그인·신청·결제는 대신 실행하지 않는다. 권한은 activeTab과 scripting만 쓴다. 성공 기준은 대상 사용자가 같은 메뉴 찾기 과제를 원본보다 EasyWeb에서 같거나 높은 성공률로 더 빨리 끝내는 것이며, 그 전에 처음 보는 기관 페이지에서 정확도 90%·재현율 85%를 넘어야 한다. 사업은 기관 실증으로 검증하며, 개인용 확장은 그 효과를 증명하는 도구다.

**쓰기 전 2가지 확인**

> * 규칙으로 처리할 수 있는 일을 AI에게 맡기고 있지 않은가 → 분류·순위는 규칙으로 한다. 소형 모델·LLM 시험에서 규칙보다 낮았다 ([09](09_local_ai_review.md))
> * 틀린 카드를 보여 줬을 때 사용자가 알아챌 수 있는가 → 카드에 "찾은 메뉴 이름"과 연결 사이트·새 창 여부를 함께 보여 주고, 원본 화면으로 바로 돌아갈 수 있게 한다

**다음 단계** — 이 PRD v2는 개발자 진술까지 반영했지만, 아직 사용자 관찰 없이 쓴 버전입니다. [03 사용자 조사](03_user_research.md)에 첫 관찰이 쌓이면 Q1·Q2·Q6를 다시 씁니다. 개발 방법은 [08 개발 계획안](08_dev_plan.md)에 있습니다.
