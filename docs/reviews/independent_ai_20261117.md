# 처음 보는 사이트로 확인한 카드 선택 방식

EasyWeb · 2026-11-17 · v0.11 작업 중 · 진단용 (제품 코드 변경 없음)

## 한 줄 결론

- 처음 보는 16개 사이트 89쪽에서 **지금 엔진은 필수 기능의 41.4%** 를 첫 화면에 넣었습니다. 개발 자료에서 쟀던 41.3%와 거의 같아서, 지난 개선이 개발 자료에만 맞춘 결과는 아니었습니다.
- **작은 학습 모델(1MB·2ms)을 엔진과 섞으면 48.2%** 로 올랐습니다(+6.8%p, 95% 구간 +2.2~+13.2). 개발 자료에서 본 효과가 처음 보는 사이트에서도 다시 나타났습니다.
- **큰 LLM의 선택으로 작은 모델을 가르치는 방법(증류)은 효과가 확인되지 않았습니다**(43.7%, 구간이 0을 포함).
- 큰 LLM(gemma4:12b)을 직접 쓰면 57.9%로 가장 높지만 한 페이지에 약 20초가 걸려 사용자 컴퓨터에는 맞지 않습니다.
- 모든 기준은 Claude 검토자입니다. 실제 사용자 관찰은 여전히 0건입니다.

"섞음"은 엔진이 게시판·게시글·관문으로 판단한 쪽은 엔진 카드를 그대로 쓰고, 나머지 쪽만 모델이 고르는 방식입니다. 자주 쓰는 버튼 줄은 모든 방식에서 엔진 그대로입니다.

- 게시판·게시글은 엔진의 페이지 유형 규칙이 이미 잘합니다.
- 차이는 **서비스 안내·오시는 길·안내 문서**에서 납니다. 엔진은 이 쪽들을 따로 알아보지 못하고 기본 규칙으로 고릅니다(엔진 판단: 기본 66쪽, 게시판 15쪽, 게시글 8쪽).
- **홈은 어떤 방식도 40% 안팎**입니다. 큰 LLM도 홈은 엔진보다 낫지 않았습니다.

## 3. 해석

- **작은 학습 모델의 효과는 진짜일 가능성이 높습니다.** 개발 자료(+6.4%p)와 처음 보는 사이트(+6.8%p)에서 비슷하게 나왔고, 두 번 모두 구간이 0보다 큽니다.
- **증류가 안 된 이유 (추정):**
  - 큰 LLM과 Claude 검토의 일치가 절반 정도(개발 자료에서 51%)라, 학습 라벨에 잡음이 많습니다.
  - 큰 LLM은 쪽마다 정확히 6개를 고르므로, 6개가 넘거나 모자란 쪽에서 정답과 어긋납니다.
  - 라벨을 붙인 쪽이 약 230쪽으로 적습니다.
- **큰 LLM 점수에는 거품이 있을 수 있습니다.** 정답을 만든 것도 LLM(Claude)이라, LLM끼리 비슷하게 고르는 경향이 점수에 섞였을 수 있습니다.

## 4. 한계

- 기준은 Claude 검토자 1명/쪽입니다. 같은 쪽을 두 검토자가 따로 보고 맞춰 보지 않았습니다.
- 89쪽, 16곳입니다. 유형별 수치는 쪽 수가 적어 흔들림이 큽니다.
- 일부 쪽은 이름과 실제 내용이 다릅니다(예: 경북대 "post"는 로그인 화면, 성남 "faq"는 로그인 화면, 광주 "location"은 정원표). 검토자는 실제 내용 기준으로 유형을 붙였고, 그대로 채점했습니다.
- 시간은 개발용 Mac(M4 Pro) 기준입니다.

## 5. 다음에 할 수 있는 것 (결정 전)

1. **작은 모델을 제품에 넣는 실험 빌드:** 엔진이 기본 규칙만 쓰는 쪽(서비스 안내·오시는 길·안내 문서)에서만 순서를 정하게 합니다. 이미 찾은 후보 안에서만 고르고, 위험·stale 차단과 게시판·게시글·관문은 규칙이 정합니다. 모델은 정적 JSON 1MB 이하, 외부 호출 없음.
2. **증류는 지금 방식으로는 보류.** 다시 한다면 LLM 순위 점수 사용, 두 모델이 일치한 것만 라벨로, 더 많은 쪽이 필요합니다.
3. **홈 쪽은 모델보다 규칙 쪽 연구가 필요합니다.** 어떤 방식도 40% 안팎입니다.
4. 사람 관찰(가족·지인)은 사용자 결정대로 마지막 단계에서 합니다.
