# 사업성 검토 — 공공 쪽 쓰임새와 유료 API 사용안

EasyWeb · 2026-11-18 · v0.11 작업 중 · 결정 전 검토

> 이 문서는 탁상 검토입니다. **기관 담당자 인터뷰 0건, 실제 사용자 관찰 0건, 경쟁 서비스 직접 사용 0건**입니다. 아래 시장·제도 내용은 2026-11-18 웹 검색으로 확인한 기사·공개 자료 요약이고, 원문 조항은 확인하지 않았습니다(10절 출처). 비용은 공개 가격표와 우리 측정값으로 계산한 추정입니다.

## 한 줄 결론

1. **돈을 낼 쪽은 기관이 맞고(D2 유지), 기관이 사는 것은 "확장 프로그램"보다 "자기 홈페이지에 붙는 쉬운 화면"과 "그 구성을 만드는 일"입니다.**
2. **유료 API는 "사용자가 페이지를 열 때마다 부르는 방식"보다 "기관 공개 페이지를 미리 한 번 분석해 두는 방식"이 맞습니다.** 비용이 사이트당 월 수백~수만 원으로 작고 예측할 수 있으며, 사용자 쪽에서 외부로 나가는 정보가 없습니다.
3. **API 비용은 걸림돌이 아닙니다.** 걸림돌은 개인정보·보안 규정, 조달 절차(CSAP 등), 그리고 "접근성 오버레이" 비판입니다.
4. 개인용 확장은 계속 **무료·로컬**(규칙 엔진 + 1MB 작은 모델)로 두는 것을 권합니다.
5. **방문 현장(도서관 어르신 PC석·디지털 체험 공간·주민센터 셀프 PC)에서는 규칙이 기본이고, 규칙이 필요하다고 판단한 쪽(서비스 안내·오시는 길·안내 문서·FAQ)에만 AI를 부르는 구성**을 검토했습니다. 비밀번호·인증·결제 화면은 AI로 보내지 않습니다. 비용은 무료 한도(OpenRouter 무료 모델)를 먼저 쓰고, 사람이 몰릴 때만 유료 한도를 둡니다(7절).

## 3. 공공에서 어디에 쓰는 것이 맞나

### 후보 비교

| # | 쓰는 곳 | 누가 돈을 내나 | 맞는 정도 | 이유 |
| :---- | :---- | :---- | :---- | :---- |
| P1 | **고령 이용자가 많은 기관 홈페이지** (지자체 민원·복지, 국민연금·건강보험 같은 공단) | 기관 홈페이지 운영 부서 | **가장 맞음** | 우리 조사에서 효과가 큰 쪽(서비스 안내·오시는 길·게시판)이 바로 이 사이트들. 기관 담당자가 카드 구성을 확정하면 품질 문제를 사람이 막음 |
| P2 | **AI디지털배움터·복지관·주민센터 공용 PC** | 사업 운영 지자체·복지관 (소액) | 맞음 (매출은 작음) | 고령층이 이미 모여 있음. 설치형 확장을 교육 도구로 씀. **사람 관찰을 할 수 있는 현장**이라는 가치가 큼 |
| P3 | **기관 웹 담당자용 진단 보고서** ("고령 사용자가 첫 화면에서 찾기 어려운 기능" 목록) | 홈페이지 개편·KRDS 적용 사업 예산 | 맞음 | 공개 페이지만 분석, 일회성, 사용자 데이터 없음. 다만 접근성 진단 업체와 겹칠 수 있음(직접 조사 0건) |
| P4 | 대학 홈페이지 | 대학 | 보통 | 대상이 고령층보다 학생·학부모 중심. 우리 조사에서 대학 쪽 필수 기능 포함률도 낮지 않음 |
| P5 | 개인에게 직접 판매 | 개인·가족 | 맞지 않음 | 고령 사용자가 설치·결제할 가능성이 낮음. 개인용은 무료로 두고 효과 증명에 씀 |

### 권장 순서

1. **P2로 시작 (무료/소액):** 배움터·복지관에서 개인용 확장을 써 보게 하고 관찰 기록을 쌓습니다. 사람 관찰은 사용자 결정대로 마지막 단계지만, 기관을 설득하려면 결국 이 기록이 필요합니다.
2. **P3으로 첫 매출:** 공개 페이지만 분석하는 진단 보고서는 보안·개인정보 부담이 가장 적고, CSAP 없이 용역으로 팔 수 있을 가능성이 있습니다(조달 방식은 **미확인**).
3. **P1이 본 사업:** 기관 홈페이지에 붙는 쉬운 화면 모듈 + 담당자 확정 카드 구성. CSAP·접근성 정책을 넘어야 하므로 실증 사업으로 먼저 들어갑니다.

## 4. 유료 API 사용안

### 비용 기준 (추정)

- 한 페이지 입력: 우리 측정 중앙값 약 3,000토큰, 긴 페이지(p90) 약 7,000토큰(Ollama 모델 토크나이저 기준, Claude 토크나이저와 다를 수 있음). 출력은 번호 6개 JSON 약 50토큰.
- 가격(100만 토큰당 입력/출력, 2026-11 기준): Haiku 5.5 $0.10/$0.50, Sonnet 5.5 $2/$10, Opus 5.5 $4/$20. 일괄 처리(Batch)는 50% 할인. Opus 5.5는 생각(thinking)을 끌 수 없어 출력 300토큰을 더한다고 가정.
- 환율 1달러 = 1,450원으로 가정.

| 모델 | 한 페이지 (보통) | 한 페이지 (긴 페이지) |
| :---- | ---: | ---: |
| Haiku 5.5 | 약 0.5원 | 약 1원 |
| Sonnet 5.5 | 약 9원 | 약 21원 |
| Opus 5.5 | 약 28원 | 약 51원 |

### 사용안 비교

| 안 | 방식 | 월 비용 예 (보통 페이지 기준) | 개인정보·보안 | 운영 부담 | 판단 |
| :---- | :---- | :---- | :---- | :---- | :---- |
| A. 실시간 (개인용) | 사용자가 페이지를 열 때마다 우리 서버가 API 호출 | 1인 월 300쪽: Haiku 141원 · Sonnet 2,828원 · Opus 8,265원. **사용자 1만 명: Haiku 141만 원 · Sonnet 2,828만 원 · Opus 8,265만 원** | 사용자가 본 페이지 주소·메뉴 이름이 서버로 감. 로그인 뒤 화면엔 이름 등 개인정보가 섞일 수 있음. PRD 원칙과 충돌 | 서버·키·남용 방지·개인정보 처리방침을 1인이 운영 | **권장하지 않음** |
| B. 공유 캐시 (개인용) | 공개 페이지 주소별 결과를 저장해 여러 사용자가 같이 씀 | 서로 다른 공개 페이지 월 5만 쪽: Haiku 2.4만 원 · Sonnet 47만 원 · Opus 138만 원 | 방문 주소가 서버로 감(동의 필요). 로그인 뒤 화면은 제외해야 함 | A보다 적지만 서버 운영 필요 | 조건부 |
| **C. 기관 사전 생성** | 기관 공개 페이지 목록을 한 번에 분석해 카드 초안 생성 → 담당자 확인 → 정적 파일로 배포 | 사이트 2,000쪽 월 1회 (Batch): Haiku 471원 · Sonnet 9,425원 · Opus 2.8만 원. 100개 사이트 × 3,000쪽 × 월 2회: Sonnet 283만 원 | 사용자 쪽에서 외부로 보내는 것 없음. 분석 대상은 공개(O) 정보 | 기관당 한 번 설정, 이후 정기 갱신 | **권장** |
| D. 사용자 키 (BYOK) | 사용자가 자기 API 키 입력 | 사용자 부담 | 사용자 책임 | 고령 사용자가 키를 관리할 수 없음 | 맞지 않음 |

### 왜 C인가

- **비용이 사용자 수가 아니라 페이지 수에 비례**합니다. 이용자가 늘어도 비용이 그대로라 기관 예산으로 정하기 쉽습니다.
- **사람이 확정**합니다. 모델이 틀린 카드를 고르면 담당자가 고칩니다. 지금 가장 좋은 방식도 필수 기능을 58% 정도만 넣으므로 사람 확인은 필수입니다.
- **작은 모델의 학습 자료가 생깁니다.** 담당자가 확정한 카드 구성은 사람이 검증한 정답입니다. 증류가 실패한 원인(LLM 라벨 잡음)을 풀 수 있는 유일한 경로입니다.
- **사용자 쪽은 지금과 같습니다.** 확정 구성이 없는 사이트에서는 규칙 엔진 + 작은 모델이 그대로 동작합니다.

### 토큰 한도 설계 (C 기준, 권장값)

| 한도 | 값 (제안) | 넘으면 |
| :---- | :---- | :---- |
| 한 요청 입력 | 페이지 요소 최대 300줄(약 8,000토큰), 출력 최대 256토큰 | 300줄에서 자르고 "잘림" 표시 |
| 사이트당 월 | 쪽 수 × 갱신 횟수로 미리 계산한 예산 + 20% (예: 3,000쪽 × 2회, Sonnet Batch ≈ 3만 원 → 한도 3.6만 원) | 새 분석 중단, 이전 확정 구성 유지 |
| 조직 전체 월 | API 콘솔의 지출 한도 + 우리 쪽 누적 계산 두 겹 | 모든 배치 중단, 알림 |
| 다시 분석 | 페이지 내용이 바뀐 경우만 (지문 비교) | 바뀌지 않은 페이지는 호출 안 함 |

A·B를 하게 된다면: 사용자당 하루 30쪽, 전체 월 예산 고정, 한도를 넘으면 규칙 엔진으로 자동 전환, 로그인 뒤 화면·입력 영역은 절대 보내지 않음.

### 모델 선택

- **품질은 아직 모릅니다.** Claude API로 이 과제를 잰 적이 없습니다.
- **재기 쉽습니다.** 처음 보는 89쪽 전체를 긴 페이지 기준으로 돌려도 Haiku 약 $0.06, Sonnet 약 $1.3, Opus 약 $3.1입니다.
- **다만 결과가 부풀 수 있습니다.** 정답을 만든 검토자도 Claude라서, Claude API 점수는 실제보다 좋게 나올 수 있습니다. 같은 Claude 계열끼리 비슷하게 고르기 때문입니다. 사람이 확정한 구성(C에서 생김)이나 사람 관찰로 다시 확인해야 합니다.

## 5. 개인용 확장은 어떻게 하나

- **무료·로컬 유지를 권합니다.** 규칙 엔진에 1MB 작은 모델을 더하는 방식으로, 외부 호출이 없습니다.
- **PRD 원칙을 지킵니다.** "분석 결과를 외부로 보내지 않는다"는 원칙을 그대로 둡니다.
- **사업에서의 역할이 바뀝니다.** "효과 증명 + 배움터 교육 도구"로 씁니다.
- **기관이 확정한 구성을 받는 방법 (나중에 결정):** 해당 기관 사이트에서는 그 구성을 우선 씁니다. 받는 길은 두 가지입니다.
  - 공개 정적 파일로 받는 방법: 권한이 추가로 필요한지 미확인입니다.
  - 확장에 묶어서 배포하는 방법

## 7. 추가 검토 — 방문 현장에서 어르신이 직접 쓰는 경우 (같은 날, 사용자 질문 반영)

### 질문

- 어르신이 집에서 하고 싶은 일은 주민센터에 가서 직원이 대신 해 주던 일입니다. 주민센터 창구에서는 직원이 해 주므로 EasyWeb을 쓸 일이 거의 없습니다.
- 그래서 따로 봅니다. 어르신이 **기관 공간을 방문해서, 기관이 마련한 PC를 본인이 직접** 쓰는 자리가 있는지, 그 자리에서 AI 비용을 정해진 한도 안에 묶을 수 있는지입니다.
- 사용자 의도는 **개인도 기관도 우선 과금 없이**, 기관에 사람이 많이 몰릴 때만 유료 한도를 두는 것입니다.

### 기준으로 삼을 세 곳

| 장소 | 어르신이 직접 쓰나 | 적합도 | 메모 |
| :---- | :---- | :---- | :---- |
| 공공도서관 어르신 PC석 | 예. 도움 없이 혼자 | 중간 | 여는 사이트가 제각각이라 미리 분석해 둘 수 없음. 이용량 미확인 |
| 디지털 체험 공간 (지자체 디지털 체험관 등) | 예 | 높음 | 곳이 적음. 실제 운영 현황 미확인 |
| 주민센터 셀프 민원 PC·대기 공간 | 드묾. 대개 직원이 대신 함 | 낮음~중간 | 기관이 "직원 손 덜기"를 원할 때만 의미. 셀프 PC가 있는 곳의 수 미확인 |

- 세 곳 모두 **기관이 관리하는 PC**입니다. 설치와 설정을 직원이 한 번 해 두면 어르신은 켜서 쓰기만 하면 됩니다.
- 공용 PC는 사양이 낮을 가능성이 큽니다. 효과가 컸던 gemma4:12b는 7.7GB이고 개발용 Mac에서도 한 쪽에 약 20초가 걸렸습니다. 그래서 이 자리에서는 로컬 큰 모델보다 외부 API가 현실적입니다.
- 무인민원발급기는 웹이 아니라 키오스크라 범위 밖입니다.

### 구조: 규칙이 기본, AI는 규칙이 필요하다고 판단한 곳에만

**AI에 절대 보내지 않는 것 (규칙이 먼저 막음)**

| 경우 | 처리 |
| :---- | :---- |
| 비밀번호 칸이 있는 페이지, 로그인·본인 인증·결제 화면 | 페이지 통째로 호출 안 함. 규칙 카드만 보여 줌 |
| 입력 칸 내용 (input·textarea 등) | 지금처럼 아예 읽지 않음 |
| 로그인 뒤 개인 화면 (마이페이지, 신청 내역 등) | 호출 안 함 |
| 이름·전화번호·주민번호처럼 보이는 글자 | 보내기 전에 지움 |
| 주소에 알 수 없는 긴 값(토큰 등)이 붙은 페이지 | 호출 안 함 |

- 비밀번호를 쓰는 단계는 지금처럼 **원본 위치 안내**만 합니다. 로그인과 인증은 대신하지 않습니다(PRD 원칙 그대로).
- 입력은 어르신이 직접 하고, 막히면 현장 직원이 돕습니다.
- 공용 PC에서 공동인증서는 위험하므로, 휴대폰 간편인증 쪽으로 안내하는 것은 기관 운영 안내의 몫입니다.

**AI를 부르는 조건 (처음 보는 89쪽 측정 근거)**

| 페이지 (엔진 판단 기준) | 엔진 | gemma4:12b 섞음 | 맡는 쪽 |
| :---- | ---: | ---: | :---- |
| 게시판 | 67.6% | 79.4% | 규칙. 이미 높고 호출 비용을 아낌 |
| 게시글 | 70.4% | 70.4% | 규칙. 차이 없음 |
| 홈 | 37.9% | 37.9% | 규칙. AI도 못 올림 |
| 서비스 안내 | 20.4% | 61.1% | **AI** |
| 오시는 길·조직 | 35.0% | 58.3% | **AI** |
| 안내 문서 | 24.4% | 48.8% | **AI** |
| FAQ | 34.2% | 50.0% | **AI** |

표의 유형은 검토자가 붙인 유형이고, 실제 제품에서는 엔진이 "기본 규칙밖에 쓸 게 없다"고 판단한 쪽이 AI 대상이 됩니다. 두 기준이 얼마나 겹치는지와, 이 조건으로 거른 결과의 품질·호출 수는 아직 재지 않았습니다.

**순서**

1. 위의 금지 조건에 걸리면 규칙만 씁니다.
2. 엔진이 게시판·게시글·관문·홈으로 판단하면 규칙만 씁니다.
3. 나머지 쪽은 AI 대상입니다.
   - 같은 페이지의 저장된 결과가 있으면 그것을 씁니다.
   - 한도가 남아 있으면 AI를 부릅니다.
   - 한도를 넘었거나 AI가 막히면 1MB 작은 모델, 그것도 없으면 규칙을 씁니다.

**AI의 역할도 좁힙니다**

- AI는 규칙이 이미 걸러 낸 안전한 후보 안에서 **순서만** 정합니다.
- 새 버튼을 만들거나 원본 동작을 실행하지 않습니다.
- 위험 동작 차단, stale 차단, 「자주 쓰는 버튼」 줄은 계속 규칙이 맡습니다.
- 답이 이상하면(없는 번호 등) 버리고 규칙 결과를 씁니다.

### 비용 단계: 무료 한도 우선

**OpenRouter 무료 모델 조건 (2026년 자료, 대부분 제3자 글. 공식 문서로 재확인 필요)**

- 무료 모델(`:free`)은 분당 20회까지 부를 수 있습니다.
- 하루 한도는 그동안 산 크레딧 합계에 따라 다릅니다.
  - $10 미만이면 하루 50회입니다.
  - 한 번이라도 $10 이상 샀으면 하루 1,000회입니다. 산 크레딧은 남고, 무료 모델만 쓰면 줄지 않습니다.
- 무료 모델도 **계정과 키가 필요합니다.** 로그인 없이 키를 받는 방법은 없습니다.

**개인 (과금 없음)**

| 단계 | 어르신이 할 일 | 내용 |
| :---- | :---- | :---- |
| 기본 | 없음 | 규칙 + 1MB 작은 모델. 외부 호출 없음 (처음 보는 사이트 +6.8%p) |
| 선택: 본인 무료 키 | 자녀·강사가 한 번 OpenRouter 가입 후 키 입력 | 하루 50쪽까지 AI. AI 대상 쪽만 부르므로 한 사람에게는 충분할 가능성이 큼(미확인). 넘으면 기본으로 자동 전환 |

**기관 방문 현장**

| 단계 | 조건 | 내용 |
| :---- | :---- | :---- |
| 1. 무료 | 기본 | 기관 계정 1개 + $10 한 번 충전(약 1.45만 원, 크레딧으로 남음) → 무료 모델 하루 1,000회. 기관 안에서는 같은 페이지 결과를 공유 |
| 2. 유료 한도 | 하루 1,000회로 부족할 때만 | 유료 모델 키를 따로 만들고 금액 한도를 걺 |

참고로, 유료 단계에서 좌석 1대가 하루 200쪽씩 월 22일(4,400쪽) 쓴다고 넉넉하게 잡으면 월 비용은 이렇습니다.
- Haiku 5.5: 약 2,100원
- Sonnet 5.5: 약 4.1만 원
- Opus 5.5: 약 12만 원

### 키를 어디에 두나

| 방법 | 어르신 입장 | 위험 | 판단 |
| :---- | :---- | :---- | :---- |
| 기관 PC에 Chrome 관리 정책으로 키 배포 | 켜면 바로 동작 | 잘 아는 사람은 빼낼 수 있음. 대신 그 키의 한도만큼만 손해 | 시범에 가장 빠름. 좌석마다 낮은 한도 키 |
| 중계 서버가 키 보관, PC에는 기관 코드만 | 켜면 바로 동작 | 키가 PC에 없음 | 정식 운영. 서버 운영·개인정보 처리방침 부담 |
| 확장 프로그램 안에 키 내장 | 켜면 바로 동작 | 누구나 빼내 다른 용도로 씀 | 하지 않음 |

**하지 않는 것: 설치마다 개인 키 자동 발급**
- 서버가 하위 키를 만들어 주는 것은 기술적으로 가능합니다. 그래도 하지 않습니다.
- 로그인이 없으면 설치를 흉내 내 키를 대량으로 받아 갈 수 있습니다.
- 무료 계정을 여러 개 만들어 한도를 늘리는 것은 약관 위반일 가능성이 큽니다.
- 개인별 한도가 필요하면, 키 대신 **설치 번호별 사용량 한도**를 중계 서버에 둡니다.
- 기관 코드를 직원이 한 번 넣어 주면, 집에서 쓰는 것도 그 기관 예산 안에서 계산할 수 있습니다. 공공장소에서 처음 만나고 집에서 이어 쓰는 연결입니다.

### 걸리는 점

1. **무료 모델은 보장이 없습니다.** 목록이 자주 바뀌고 갑자기 막힐 수 있습니다. 그래서 규칙이 늘 뒤를 받칩니다.
2. **입력이 학습에 쓰일 수 있습니다.**
   - 일부 무료 모델 제공사는 입력을 학습에 쓰는 조건이 있습니다. 어떤 모델이 그런지는 미확인입니다.
   - 보내는 것은 로그인 전 공개 페이지의 메뉴 이름뿐이라 위험은 낮습니다. 그래도 기관의 확인과 동의가 필요합니다.
3. **여러 제공사를 거칩니다.**
   - OpenRouter는 뒤에서 여러 제공사로 요청을 넘깁니다. 기관에는 제공사를 고정하는 설정과 "데이터 수집 안 하는 제공사만" 설정이 필요합니다.
4. **한국어 품질을 모릅니다.** 무료 모델이 gemma4:12b(57.9%)만큼 하는지는 89쪽으로 재 봐야 압니다.
5. **권한과 원칙이 달라집니다.**
   - 외부 API 주소 접속 권한이 새로 필요합니다. 개인용 기본 빌드에는 넣지 않고, 키를 넣고 켠 경우나 기관용 빌드에만 둡니다.
   - PRD 원칙도 "사용자나 기관이 키를 넣고 켠 경우에만, 공개 페이지 메뉴 이름만 보냄"으로 고쳐야 합니다(D15). 이는 01·08을 먼저 고칠 일입니다.
6. **집에서는 PC만 해당합니다.** 모바일 Chrome은 PRD에서 제외되어 있습니다. 어르신이 집에서 PC와 휴대폰 중 무엇으로 일을 보는지는 미확인입니다.

**우리 시나리오에 대입하면**

- **개인 (집, 과금 없음):**
  - 기본은 규칙과 1MB 모델입니다.
  - 선택으로 자녀나 강사가 무료 키 하나를 넣습니다. 후보는 OpenRouter, Gemini, K-엑사원 중 하나입니다.
  - Chrome 내장 AI가 한국어를 지원하면 키 없이 쓰는 1순위가 됩니다.
- **기관 방문 현장:**
  - 중계 서버(Cloudflare Workers 같은 곳)에 키를 두고, 무료 한도를 먼저 씁니다.
  - 무료 단계는 OpenRouter $10 계정(하루 1,000회)이나 Workers AI 무료 몫으로 시작합니다.
  - 입력 학습 조건이 있는 무료 등급(Gemini 무료, K-엑사원)은 기관 동의 없이 쓰지 않습니다.
- **여러 무료 제공사를 차례로 시도할 수 있습니다.** 한 곳이 막히면 다음 곳, 모두 막히면 규칙으로 갑니다.
  - 다만 한 제공사에 계정을 여러 개 만들어 한도를 늘리는 것은 하지 않습니다.
- **어느 무료 모델도 우리 과제(한국어 메뉴 고르기) 품질은 재지 않았습니다.**

### 방향 수정: 분석은 우리 쪽 로컬 모델로 미리, 사용자는 결과만 받기 (같은 날, 사용자 결정 전 제안)

사용자 제안은 이렇습니다. 사이트 분석은 우리 쪽에서 로컬 모델로 해서 결과를 서버에 계속 올려 두고, 사용자가 실제로 여는 페이지나 요청한 페이지 순서로 분석을 늘려 갑니다. 결과가 없는 페이지에서 어떻게 할지는 따로 풉니다.

```
[우리 쪽]  수집기(별도 headless, 로그인 안 함) → 엔진 + gemma4:12b → 사이트 단위 결과 파일 → 정적 서버
[사용자]   결과 목록에 있는 사이트면 그 사이트 파일을 받음 → 지금 화면 후보와 고정 표시로 맞춰 봄 → 카드
```

- **API 비용 0원:** 처리량은 한 쪽에 약 20초, Mac 한 대로 하루 약 4,000쪽입니다.
- **gemma가 느린 문제는 구조로 풉니다.** 사용자는 기다리지 않고, 모델은 우리 쪽에서 미리 돕니다.
- **방문 기록을 알리지 않습니다.** 페이지마다 묻지 않고 사이트 단위 파일을 받습니다. 결과가 있는 사이트 목록은 확장에 같이 넣어, 목록에 없는 사이트는 아예 묻지 않습니다.
- **원칙 변경이 필요합니다.** 사용자 쪽에서 결과 파일을 받는 외부 요청이 생기므로, PRD 원칙을 01·08에서 먼저 고쳐야 합니다(D15·D17).

**결과가 없는 페이지 (제안 순서)**

| 순서 | 방법 | 근거 |
| :---- | :---- | :---- |
| 1 | 즉시 규칙 + 작은 학습 모델 | 1MB 로지스틱 47.5%(2ms) → 순위 학습 52.0%(약 4ms, 확인 3) |
| 2 | 같은 사이트의 같은 틀 페이지 결과 재사용 | 미측정 |
| 3 | "분석 요청" 버튼 → 주소만 보냄 → 다음 방문부터 모든 사용자에게 결과 | 다음 방문부터 gemma 수준. 누를 때만 전송, 로그인 뒤 화면은 요청 불가 |
| 4 | 선택: 본인 무료 키로 즉시 AI | 미측정 |
| 5 | 나중: Chrome 내장 AI (한국어 지원 시) | 미측정 |

**확인 1: 저장한 결과가 다음 수집에서도 맞나 (2026-11-18, 외부 AI 호출 없음)**

- **방법:** 11-17에 모은 평가용 16곳을 11-18에 같은 시드와 별도 headless로 다시 모았습니다([recollect](../evidence/run010/stability-20261118/recollect)). 11-17의 선택을 번호가 아니라 고정 표시로 바꿔, 새 화면에서 하나로만 다시 찾아지는지 셌습니다([stability-check.mjs](../../scripts/ml/stability-check.mjs), [stability.json](../evidence/run010/stability-20261118/stability.json)).
- **페이지:** 89쪽 중 83쪽은 주소가 같았습니다. 5쪽은 주소가 바뀌었고 1쪽은 수집되지 않았습니다. 대부분 최신 글이 바뀐 게시글 쪽과 행정안전부 쪽입니다.

| 고정 표시 | gemma4:12b 선택 494개 | 엔진 카드 443개 |
| :---- | ---: | ---: |
| 이름 + 짧은 주소 + 영역 + 같은 표시 중 순서 | **98.8%** | 98.2% |
| 이름 + 짧은 주소 + 영역 | 91.7% | 93.7% |
| 이름 + 짧은 주소 | 86.4% | 87.8% |
| 이름만 | 84.2% | 86.0% |

- **해석:** 같은 링크가 한 페이지에 여러 번 나오는 경우가 많아서, 순서까지 넣어야 거의 다 찾습니다. 순서를 넣으면 하루 뒤에 99% 가까이 다시 찾았습니다.
- **한계:** 간격이 하루뿐입니다. 사이트 개편 뒤나 몇 주 뒤에는 더 떨어질 수 있습니다. 주기적인 재수집과 "맞는 비율이 낮으면 결과 없음 처리"가 필요합니다.

**확인 2: Jev처럼 가벼운 순위·분류 모델이 더 있나 (2026-11-18 검색 + 로컬 시험)**

사용자 판단대로, 핵심은 "엔진이 이미 찾은 버튼 중 무엇이 가장 중요한가"의 순위입니다. 그래서 문장을 만들지 않고 점수만 내는 작은 모델을 찾았습니다. 그중 바로 돌릴 수 있는 것은 개발 134쪽에서 학습 없이(제로샷) 시험했습니다([ondevice-rerank.mjs](../../scripts/ml/ondevice-rerank.mjs), [점수](../evidence/run010/stability-20261118/rerank-dev-score.json)).

| 종류 | 모델 (크기) | 결과 (개발 134쪽, 섞음) |
| :---- | :---- | :---- |
| 지금 엔진 | — | 37.2% |
| 리랭커, 학습 없이 | cross-encoder/mmarco-mMiniLMv2 (약 1.2억) | 34.3% (−5.7 ~ −1.0%p, **엔진보다 낮음**). 한 쪽 49ms |
| 리랭커, 학습 없이 | Horizon-Labs/multilingual-reranker-small | 35.7% (−3.4 ~ +0.3%p). 한 쪽 120ms |
| 리랭커 | jina-reranker-v2 다국어 (2.8억), gte 다국어 리랭커 (3억) | 우리 도구(transformers.js 3.8.1)가 구조를 지원하지 않아 못 돌림 |
| 리랭커 (한국어 조정판 포함) | bge-reranker-v2-m3(-ko) (5.7억), Qwen3-Reranker-0.6B, jina-reranker-v3 (6억) | 크기·형식 때문에 이번에 시험 안 함 |
| 학습 없는 분류 | GLiClass 다국어 mini (약 2.9억) | 시험 안 함. 한국어 학습 여부 미확인 |
| Jev 비슷한 결정 모델 | jeff (4억), selfjev-4b, OpenJev | 커뮤니티 구현, 라이선스·성숙도 미확인 ([09](../09_local_ai_review.md)) |
| **우리 자료로 학습한 작은 모델** | 글자 조각 + 위치 특징 로지스틱 (약 1MB) | **43.6%** (+2.6 ~ +10.4%p), 처음 보는 쪽 48.2%. 한 쪽 2ms |

- **점수를 올리는 것은 모델 크기가 아니라 우리 과제로 학습했느냐입니다.** 1MB 학습 모델이 1억 개 넘는 매개변수의 리랭커보다 높았습니다.
- **미리 분석하는 구조가 학습 자료를 계속 만듭니다.** gemma 결과와, 나중에 사람이 확정한 결과입니다. 이걸로 1MB 모델(결과 없는 페이지용)을 계속 다시 학습하는 고리가 됩니다. 다만 지난 증류 시험(LLM 라벨만으로 학습)은 효과가 확인되지 않았으므로, 사람 확정 라벨이 섞여야 할 가능성이 큽니다.
