## 3. 개발 원칙

1. **근거 없는 기능을 만들지 않는다.** 페이지에 실제로 있고 근거가 있는 제어만 카드로 만든다.
2. **사이트별 정답을 외우지 않는다.** 평가 ID·문서 번호·불투명 query·정답 순서·사이트 이름으로 규칙을 만들지 않는다. 구조·역할 같은 일반화 가능한 근거만 쓴다.
3. **기준을 낮추지 않는다.** 결과가 나쁘면 기준이 아니라 엔진을 고친다. 첫 실패는 기록으로 남긴다.
4. **안전 검사를 먼저, 관계 근거는 그 뒤에.** 위험 URL/query/script 검사를 읽기 예외로 우회하지 않는다.
5. **캐시는 한 번의 분석 묶음 안에서만.** 다음 카드·메뉴·초점·현재성 검사마다 새로 계산한다.
6. **검증 종류는 서로 대신하지 않는다.** ([05](05_handoff.md) 검증 경계)

## 4. 검증 방법

| 무엇을 | 명령 | 언제 |
| :---- | :---- | :---- |
| 타입·빌드·로컬 회귀·core 품질·합성 성능 | `npm run verify` | 코드 변경마다 |
| 두 모드 × 60페이지 개발 비교 | `npm run compare:development -- --output-dir=<새 빈 경로>` | 분류·순위 변경 후 |
| 자동 접근성 21조건 | `npm run test:a11y` | 화면 변경 후 |
| 실제 공개 사이트 15과제 | `npm run test:tasks` | 원본 연결 변경 후 (외부 사이트 영향) |
| 처음 보는 자료 첫 평가 | `npm run evaluate -- --phase=fresh-blind-validation --engine-freeze=… --dataset-freeze=… --output-dir=<새 경로>` | 엔진 동결 후 1회 |
| 패키지 재현성 | `npm run package` | 버전 마감 시 |
| 분류 진단 (선택) | `node scripts/ml/extract-dataset.mjs` → `scripts/ml/train.py` | 오분류 검토 시 |

같은 통과 검사를 근거 없이 반복하지 않습니다. 실패한 첫 실행은 지우지 않고 보존한 뒤 다시 실행합니다.
