## 1. 왜 나누나

지금 엔진은 어떤 페이지든 같은 규칙으로 고릅니다: "근거가 있는 후보 중 6개 분류(로그인·검색·공지·학사·신청조회·이용안내)에서 골고루". 그래서 이런 일이 생깁니다.

| 페이지 | 검토자가 원한 것 | 엔진이 준 것 | 원인 |
| :---- | :---- | :---- | :---- |
| 홈 | 대표 서비스 (예상연금액 조회, 민원신청) | 지사찾기 2번, 신청하기 | 홈에서 "대표 서비스"를 구분할 칸이 없음 |
| 게시판 목록 | 게시판 검색, 학사/장학 분류 | 게시글 제목 | 게시판에서는 글이 "공지" 근거를 가장 강하게 가짐 |
| 도움말 | 상담 신청, 국민신문고 | 개인정보처리방침, 법령정보 | "안내"라는 말만으로 이용 안내로 분류 |

**페이지 유형마다 "무엇을 보여 줄 칸"을 미리 정해 두고, 그 칸을 채울 후보를 찾는 방식**으로 바꾸자는 것이 이 설계입니다. 최대 6개 + 「다른 기능 보기」 정책은 그대로입니다.

## 3. 유형별 처음 6칸 구성 (초안)

칸은 "역할"입니다. 역할에 맞는 후보가 없으면 그 칸은 일반 규칙으로 채웁니다. 순서는 위에서부터.

### A. 홈 — "이 기관에서 가장 많이 하는 일" · **확정 (2026-10-31)**

| 칸 | 역할 | 검토자 근거 (5개 홈) |
| :---- | :---- | :---- |
| 1 | 사이트 검색 | 5/5 페이지에서 고름 |
| 2~3 | **대표 서비스** 2개 (빠른 메뉴·눈에 띄는 서비스 묶음에서) | 민원신청, 예상연금액 조회, 내 국민연금, 수강신청, 대피시설, 책이음 |
| 4 | 소식 **목록** 1개 (게시글 아님) | 소식알림, 재난문자 더보기, 통합공지 더보기 |
| 5 | 로그인 (있으면) | 4/5 |
| 6 | 찾아오시는 길·상담·이용 안내 중 1개 | 오시는 길, 채팅상담, 검색방법 |

다른 메뉴: 나머지 대표 서비스, 다른 게시판 목록, 회원가입 등. **개별 게시글·배너·슬라이드는 넣지 않음.**

**일부 구현 (2026-11-12):** 홈에서만 「자주 찾는 서비스·주요 서비스·빠른 메뉴·서비스 바로가기」 제목 아래의 일반 링크를 대표 서비스 후보로 읽는다(이름이 분류어와 안 맞아도). 묶음 조정 버튼(설정·편집·닫기 등)과 하단 링크는 뺀다. 6번 칸 규칙에 따라 홈에서는 「찾아오시는 길」이 상담과 같은 칸을 두고 경쟁하며, 본문 우선 기능 자리를 따로 차지하지 않는다. 칸 역할별 고정 배치(1번 검색, 2~3번 대표 서비스…)는 아직 아님 ([검토](reviews/survey_fixes_20261112.md)).

### B. 게시판 목록 — "새 글 바로 읽기" · **확정 (2026-10-31)**

| 칸 | 역할 | 근거 |
| :---- | :---- | :---- |
| 1 | 게시판 검색 | 검토자 2/2 |
| 2~6 | **최신 글 5개** (원본 목록 순서대로). 누르면 그 글로 바로 이동 | 사용자 결정 (D10). 검토자는 필터를 골랐지만 사용자가 글 목록을 선택 |

다른 기능: 분류·필터(학사/장학, 캠퍼스), 다음 글들, 사이트 대표 서비스. 처음 화면·로그인은 「자주 쓰는 버튼」 줄 (아래 3-1).

**구현 (2026-11-01):** 게시판 판단 = 본문에서 한 부모 아래 5줄 이상·긴 제목·같은 글 보기 주소 틀·날짜 또는 쪽 번호. 고정 공지는 번호 글 뒤로, 같은 제목 한 번 ([사이트 조사](reviews/site_survey_20261101.md) 3절).

### 관문 — "어느 사이트로 갈지 고르기" · **구현 (2026-11-01)**

국민연금·근로복지공단·서울대병원 첫 주소가 이 유형. 화면 요소 40개 이하 + "○○ 바로가기" 큰 링크 3개 이상 → 그 링크들을 카드로 (제목은 링크 안 굵은 글자).

### I. 신청서·입력 페이지

입력칸 값은 읽지 않는 원칙 그대로. 카드는 "원본 신청서로 가기"(위치 안내) 1개 + 신청 안내·문의 + 사이트 검색 정도. 실제 제출은 원본에서만.

### 3-1. 모든 유형 공통 — 「자주 쓰는 버튼」 줄 · **구현됨 (2026-10-31)**

처음 화면·로그인·회원가입은 어느 페이지에나 있지만 홈에서만 핵심 기능입니다 (사용자 의견). 그래서:

- **홈이 아닌 페이지:** 이 셋은 6칸에 넣지 않고, 카드 위의 「자주 쓰는 버튼」 줄에 둡니다. 6칸은 모두 그 페이지의 기능에 씁니다.
- **홈:** 로그인은 A의 5번 칸 그대로 카드. 줄에는 회원가입만 (처음 화면은 지금 페이지라 없음).
- 페이지에 실제로 있는 것만, 정확한 이름("로그인", "회원가입", "홈"·"처음으로")이나 머리 영역 로고 링크만 씁니다.

## 4. 동작 방식

1. **유형 판단:** 위 근거를 점수로 모아 가장 강한 유형 하나를 고른다. 근거가 약하면 **기본**(지금 규칙).
2. **칸 채우기:** 유형의 칸 순서대로, 그 역할에 맞는 후보 중 가장 근거가 강한 것을 넣는다. 같은 기능 중복(P3)은 계속 막는다.
3. **빈칸:** 역할에 맞는 후보가 없으면 일반 규칙으로 채운다.
4. **다른 기능:** 나머지는 지금처럼 「다른 기능 보기」.

원칙은 그대로: 근거 없는 기능을 만들지 않음, 사이트별 매핑 금지, 입력값 비수집, 최대 6개.

## 5. 위험과 대응

| 위험 | 대응 |
| :---- | :---- |
| 유형을 잘못 판단하면 카드가 통째로 이상해짐 | 근거가 약하면 기본 규칙. 유형 판단을 따로 측정 (15페이지에서 유형 정답 먼저 정하기) |
| 칸 설계가 검토한 15페이지에만 맞춰짐 | 유형별 페이지가 2~5개뿐. 새 페이지(D4)로 확인 전에는 "초안" |
| 6개 분류 틀과 충돌 (대표 서비스, 찾아오시는 길, 전화) | 칸은 역할이고 분류는 카드 아이콘·설명용. "주요 서비스" 분류 추가(D9)와 함께 결정 |
| 기존 개발 평가와 어긋남 (게시판의 "특정 글 읽기" 등) | 정답표는 바꾸지 않고, 차이는 정책 변경으로 기록. 실제 페이지 유용성 측정을 함께 봄 |

## 6. 진행 순서 (제안)

1. 유형 목록과 유형별 칸 구성 확정 (사용자 결정, 07 D11)
2. 15페이지에 "유형 정답" 붙이고, 유형 판단만 먼저 구현·측정
3. 영향이 큰 유형부터 칸 채우기 구현: **홈(A) → 게시판(B) → FAQ(D) → 서비스 안내(F)**
4. 매번 실제 페이지 비교(원본 위치 매칭으로 개선 후)와 60페이지 개발 비교를 함께 실행
