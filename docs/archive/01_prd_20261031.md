## Q1. 누가 쓸까?

**학교·시청·공공기관 홈페이지에서 필요한 메뉴를 찾는 데 시간이 오래 걸리는, 웹에 익숙하지 않은 성인.** 예를 들어 시청 홈페이지에서 여권 신청 안내를 찾아야 하는데, 배너·뉴스·행사·SNS가 섞인 첫 화면에서 어디를 눌러야 할지 몰라 여러 메뉴를 열어 보는 고령 사용자.

- 지금 쓰는 사람: 개인 사용자 (Chrome 확장을 직접 설치)
- 나중에 돈을 낼 수 있는 쪽: 대학·지자체·공공기관 (지원서 Q3-2의 B2B/B2G 계획). **아직 기관 인터뷰는 0건**이라 가설입니다 → 07 D2

> 미확인: 실제 사용자를 만나 관찰한 적이 없습니다(1인 사전 시험·정식 실증 모두 0건). 위 인물은 지원서의 문제의식에서 나온 가정입니다 → [03](03_user_research.md)

## Q2. 뭐가 답답한가?

1. **찾는 것 자체가 어렵다.** 첫 화면에 로그인·조회·신청 같은 실제 업무 메뉴와 홍보 배너·뉴스·행사·SNS가 함께 있어서, 글씨를 키워도 "무엇을 눌러야 하는지"가 보이지 않는다.
2. **사이트마다 구조가 다르다.** 대학·시청·정부·공공기관·도서관이 메뉴 이름과 위치가 다 달라서, 한 사이트에서 익힌 방법이 다른 사이트에서 통하지 않는다.
3. **기존 접근성 도구는 문제를 알려줄 뿐이다.** 검사 도구는 접근성 문제를 찾아 주지만, 사용자에게 "지금 무엇을 누르면 되는지"를 보여 주지는 않는다. (지원서 Q2 · 02 벤치마킹에서 확인 필요)

## Q3. 어떻게 풀까?

**웹에 익숙하지 않은 사람이 기관 홈페이지를 쓸 수 있도록, 지금 보고 있는 페이지에서 실제로 있는 주요 기능을 찾아 큰 버튼 6개로 다시 보여 주는 Chrome 확장이에요.**

사이트를 새로 만들지 않습니다. 원래 사이트는 그대로 두고, 로그인·인증·신청은 원래 화면에서 진행합니다.

## Q4. 기능 딱 3개?

1. **주요 기능 찾기:** 확장 버튼을 누르면 현재 페이지의 보이는 링크·버튼·검색창을 읽고, 로그인 · 검색 · 공지사항 · 학사정보 · 신청·조회 · 이용 안내 6개 분류로 나눈다. 실제로 있는 것만 보여 주고 없는 기능은 만들지 않는다. 판단은 규칙 기반이며 근거(이름·위치·주변 제목·본문 관계)가 있는 것만 채택한다.
2. **쉬운 화면:** 처음에는 **최대 6개**를 큰 카드로 보여 주고, 필요하면 **다른 메뉴 보기 / 이전 메뉴**로 더 본다 (사용자 확정 정책). 큰 글씨, 키보드 조작, 스크린리더 안내, 좁은 화면 재배치를 지원한다. Esc나 「원본 화면 보기」로 언제든 원래 화면으로 돌아간다.
3. **원본과 안전하게 연결:** 일반 링크는 바로 이동한다. JavaScript 버튼·팝업·다운로드·로그인(SSO)·같은 페이지 안 이동은 **원본 위치를 표시**하고 사용자가 직접 누르게 한다. 원본이 바뀌었으면 낡은 카드를 막고 「다시 찾기」를 안내한다.

**가능하면 :** 기관 담당자가 중요 메뉴를 직접 지정하는 기관용 설정 (지원서 2단계), 기관 홈페이지에 바로 넣는 웹 모듈·SDK

**안 할 것 :** 로그인·결제·신청·삭제를 대신 실행, 입력한 내용 읽기, 분석 결과를 서버로 보내기, 모든 웹사이트 지원 약속, 모바일 Chrome, 브라우저 내부 페이지, AI 분류의 제품 탑재(시험 결과 규칙보다 낮음 → [09](09_local_ai_review.md))

## Q5. 어떻게 생겼나?

**한 화면 (원본 페이지 위에 덮는 쉬운 화면)** — 자세한 구성은 [06 화면](06_screens.md)

- 위: EasyWeb 이름, 「원본 화면 보기」 버튼
- 가운데 머리: 지금 보고 있는 사이트 주소, "무엇을 하시겠어요?", 설명 한 줄
- 본문: 「바로 이용하기」 아래 카드 최대 6개 (아이콘 · 분류 이름 · 설명 · 찾은 메뉴 이름 · 연결된 사이트/새 창 안내 · 「원본 페이지로 이동」 또는 「원본에서 계속하기」), 오른쪽 위 「다시 찾기」
- 아래: 「다른 메뉴 보기 / 이전 메뉴」, "로그인·인증·신청은 원래 사이트에서 진행해요."
- 상태 화면: 기능을 못 찾음 · 원본이 바뀜 · 원본 위치 안내 성공/실패

## Q6. 성공의 모습?

**대상 사용자가 같은 공개 메뉴 찾기 과제를 원본 화면보다 EasyWeb에서 같거나 높은 성공률로, 더 짧은 시간에 끝내면 성공.** 측정은 6~8명이 5개 기관 과제를 원본/EasyWeb에서 각각 수행하는 정식 실증([USER_STUDY](USER_STUDY.md))으로 한다. 성공률·완료 시간·클릭 수·오클릭을 비교한다.

기술 쪽 전제 조건 (사람 실증 전에 통과해야 함, [WORK_SPEC](WORK_SPEC.md)):
- 처음 보는 기관 페이지(독립 자료)에서 처음 6개 정확도 90% 이상 · 놓치면 안 되는 기능 재현율 85% 이상
- 분석 300ms · 화면 준비 1초 이내 (1,000개 제어 기준)
- 자동 접근성 위반 0, 실제 VoiceOver·200/400% 확대 확인

> 현재: 개발 자료에서는 기준을 넘지만, **처음 보는 자료의 첫 평가는 재현율 2/15로 실패**했습니다. 사람 실증은 0건입니다 → [07](07_todo.md)

## ＋ 필요 데이터 · 제약

- **쓸 수 있는 자료:** 5개 기관(상명대·천안시·국민안전24·국민연금공단·국립중앙도서관)의 공개 페이지. 지금까지 60페이지를 정답표로 만들었고 모두 개발에 사용함 → 새 검증에는 **새 페이지가 필요**
- **쓸 수 없는 자료:** 로그인 뒤 화면, 사용자의 입력값·계정 정보, 기관 내부 통계
- **권한:** `activeTab` + `scripting`만 사용. 사용자가 버튼을 누른 탭에서만 실행. 상시 접근·외부 서버 없음
- **실행 환경:** macOS 데스크톱 Chrome 우선. Windows Chrome은 같은 절차를 준비만 함 (미확인)
- **사람 일정:** 1인 프로젝트라 사용자 모집·관찰은 직접 해야 함. 지원서상 멘토 기관(선문대) 도움 가능 여부 미확인 → 07 D3
- **미확인:** 기관 도입 의사와 비용, 공공기관 보안·접근성 인증 요구사항 (지원서 Q4-2에서 멘토에게 묻기로 함)

## ★ 한 단락 PRD

EasyWeb은 학교·시청·공공기관 홈페이지에서 필요한 메뉴를 찾기 어려운, 웹에 익숙하지 않은 성인을 위한 Chrome 확장이다. 지금 기관 홈페이지는 업무 메뉴와 배너·뉴스·행사가 한 화면에 섞여 있고 사이트마다 구조가 달라, 글씨를 키워도 무엇을 눌러야 할지 알기 어렵다. 핵심 기능은 3가지다. 첫째, 사용자가 확장 버튼을 누르면 현재 페이지의 보이는 링크·버튼·검색창을 읽어 로그인·검색·공지사항·학사정보·신청·조회·이용 안내로 나누고, 근거가 있는 실제 기능만 고른다. 둘째, 처음에는 최대 6개를 큰 카드로 보여 주고 「다른 메뉴 보기 / 이전 메뉴」로 더 볼 수 있게 하며, 키보드·스크린리더·확대에서도 쓸 수 있고 Esc로 언제든 원본에 돌아간다. 셋째, 일반 링크는 바로 이동하고 스크립트·팝업·다운로드·인증 제어는 원본 위치만 표시해 사용자가 직접 누르게 하며, 원본이 바뀌면 낡은 카드를 막는다. 입력 내용은 읽지 않고, 분석 결과를 외부로 보내지 않으며, 로그인·신청·결제는 대신 실행하지 않는다. 권한은 activeTab과 scripting만 쓴다. 성공 기준은 대상 사용자가 같은 메뉴 찾기 과제를 원본보다 EasyWeb에서 같거나 높은 성공률로 더 빨리 끝내는 것이며, 그 전에 처음 보는 기관 페이지에서 정확도 90%·재현율 85%를 넘어야 한다.

**쓰기 전 2가지 확인**

> * 규칙으로 처리할 수 있는 일을 AI에게 맡기고 있지 않은가 → 분류·순위는 규칙으로 한다. 소형 모델·LLM 시험에서 규칙보다 낮았다 ([09](09_local_ai_review.md))
> * 틀린 카드를 보여 줬을 때 사용자가 알아챌 수 있는가 → 카드에 "찾은 메뉴 이름"과 연결 사이트·새 창 여부를 함께 보여 주고, 원본 화면으로 바로 돌아갈 수 있게 한다
