# EasyWeb v1.0 파일럿 작업명세서

작성일: 2026-10-17 (한국 시간) · 최초 기준: v0.1.0 · 현재 구현: v0.5.0 개발 후보 (RUN-004)

## 1. 진행 방식

**전체 개발은 10단계의 완료 조건으로 관리하고, 4시간은 한 번의 실행 묶음으로 사용한다.** 단계는 시간이나 토큰을 모두 썼다는 이유로 완료하지 않는다. 한 단계가 커지면 하위 작업으로 나누되 상위 단계 번호는 유지한다.

이 명세서에서 최종 개발은 **데스크톱 Chrome에서 5개 기관 사이트를 지원하는, 설치 가능한 v1.0 파일럿**까지다. 모든 웹사이트 지원, AI 분류, 기관 관리자 서버, SDK, 구독 결제, Chrome 웹 스토어 공개는 별도 후속 범위다.

작업 시작·재개 시 [진행표](PROGRESS.md)를 읽고 다음 실행 가능한 하위 작업을 선택한다. 한 번에 여러 단계의 수행을 요청받으면 단계별로 증거와 진행표를 갱신하며 계속 진행한다. 매 단계마다 추가 승인을 요청하는 방식은 사용하지 않는다. 사용자 직접 테스트가 필요한 항목은 별도 상태로 남기고, 그 항목에 의존하지 않는 작업은 진행할 수 있다.

## 2. 최초 기준선과 수정 우선순위

아래 표는 v0.1 계획 시점의 결함 기록이다. RUN-001에서 B01~B05 관련 수정을 구현·회귀 검사했으며, 당시 B04의 전체 액션 사례 검증은 S05에 남겼다. B06·B07도 당시 미해결 항목이다. v0.3.0의 후속 처리는 [RUN-002 과거 기록](RUN_002_REPORT.md), 최신 증거와 상태는 [RUN-004 보고서](RUN_004_REPORT.md)와 [진행표](PROGRESS.md)를 따른다.

2026-10-17에 타입 검사·빌드·기존 자동 테스트 **11개 통과**를 다시 확인했다. 기존 상명대 관찰은 1개 공개 홈페이지에서 학사정보·검색·로그인 3개를 찾고 화면을 표시한 결과다. 실제 도구 모음 권한 부여와 업무 완료의 증거는 아니다.

## 3. 제품 범위와 사용자 흐름

사용자가 웹사이트에서 확장 버튼을 누른다 → 현재 페이지의 주요 기능 후보를 분석한다 → 실제로 발견한 기능을 처음에는 최대 6개의 쉬운 버튼으로 보여준다 → 필요한 경우 **다른 메뉴 보기 / 이전 메뉴**로 추가 후보를 탐색한다 → 명확한 일반 링크는 목적지로 이동하고, 동작을 보장하기 어려운 제어는 원본 위치로 안내한다 → 언제든 원본 화면으로 돌아간다. 추가 메뉴 흐름은 기존 순위와 최초 6개 품질 지표를 변경하지 않는다.

| 영역 | v1.0 파일럿 요구사항 |
| --- | --- |
| 실행 | 사용자 요청 시 실행, 중복 생성 방지, 닫기·Esc·재실행 복귀, 페이지 이동 후 재실행 안내 |
| 기능 수집 | 링크·버튼·검색 제어의 안전한 이름과 주변 의미 수집, 숨김·비활성 구분 |
| 개인정보 | input·textarea·contenteditable·사용자 정의 textbox/searchbox의 실 입력값을 후보·화면·로그·저장소에 넣지 않음 |
| 분류·추천 | 키워드·URL·랜드마크·주변 제목 근거, 근거 없는 기능 생성 금지, 목적지 중복과 분류별 개수 제한을 별도로 처리. 최초 최대 6개와 추가 메뉴 탐색을 구분하며 기존 순위·최초 6개 평가 기준 유지 |
| 동적 화면 | 메뉴 교체·href 변경·SPA 경로 변경 시 낡은 후보 무효화. 재탐지 중 초점 보존 |
| 원본 연결 | 이동 가능한 링크와 원본 위치 안내의 경계를 문서화. 외부 목적지·새 창 여부 안내 |
| 원본 보존 | 임의 폼 제출·인증·결제·삭제 실행 없음. 종료 후 원본 입력·DOM·초점·스크롤 복구 |
| 접근성 | 키보드 전 경로, 초점 표시, 상태 알림, 텍스트 대비, 확대·재배치·강제 색상 점검 |
| 오류 | 탐지 없음·대상 사라짐·실행 제한 페이지에서 이해하기 쉬운 안내와 원본 복귀 제공 |
| 배포 | 재현 가능한 빌드, ZIP·버전·해시·설치/제거 안내, 지원 사이트·알려진 한계 목록 |

지원 기준은 macOS의 데스크톱 Chrome을 우선한다. Windows Chrome은 동일 절차로 검사할 수 있도록 준비하고, 실행 환경이 확보될 때 확인한다. Windows를 확인하지 않았다면 호환 완료라고 표기하지 않는다. 모바일 너비 UI 확인을 모바일 Chrome 확장 지원으로 표현하지 않는다.

iframe·닫힌 Shadow DOM·브라우저 내부 페이지는 지원 제약을 표시한다. 열린 Shadow DOM과 같은 출처 iframe도 실제 필요와 권한 범위를 확인한 뒤 지원 여부를 결정하며, 기능 확대를 위해 접근 권한을 무조건 늘리지 않는다.

### S01. 기준선·명세 확정

- 기존 코드·문서를 확인하고 타입 검사·11개 테스트를 재실행한다.
- 입력 보호 누락, DOM 변화, 분류·중복, 실제 확장 실행 증거의 차이를 기록한다.
- 완료 조건: 명세서·예산·진행표의 단계·상태·다음 작업이 일치한다. 개발 완료와 사용자 실증 완료를 구분한다.

### S02. 정답 데이터와 평가 대상 확정

- 대학 1, 지자체 1, 정부 서비스 1, 공공기관 1, 도서관 1의 **공개 사이트 5개**를 선정한다. 대학은 상명대를 유지한다. 나머지 후보는 천안시·정부24·국민연금공단·국립중앙도서관이며 현재 지원을 뜻하지 않는다. 공개 접근이 어려우면 같은 유형의 대체 사이트와 사유를 기록한다.
- 사이트당 3개 페이지, 총 **15개 페이지**를 고정한다. 페이지마다 실제로 존재하는 기능 2개 이상을 정답으로 기록하여 총 30개 이상의 기대 기능을 확보한다. 없는 로그인 메뉴 등을 기대 기능에 넣지 않는다.
- 사이트당 공개 과제 3개, 총 **15개 목적지 도달 과제**를 정한다. 로그인 후 업무, 개인정보 입력, 실제 신청·결제·제출을 포함하지 않는다.
- 문구·원본 목적지·분류·노출 조건·이동/위치 안내 기대값·수집 날짜를 기록한다. 개발 중 사용하는 페이지 10개와 평가용으로 따로 남기는 페이지 5개를 구분한다.
- 완료 조건: 정답을 먼저 확정하고 현재 버전의 정확도·누락 기준선을 계산한다. 로컬 재현에는 필요한 메뉴 구조만 사용하며 로그인 데이터·전체 사이트 사본을 저장하지 않는다.

### S03. 입력 보호와 DOM 분석 안정화

- **S03.1 B01 입력 내용 읽힘을 먼저 수정**하고 기존 input뿐 아니라 textarea·contenteditable·role textbox/searchbox·편집 요소를 포함한 버튼/링크를 검사한다. 고정된 접근성 이름·연결된 label·placeholder와 실제 입력 내용을 구별한다.
- S03.2 의미 있는 제어의 이름 추출을 보완하고 B02를 해결한다. 긴 글·본문 카드가 메뉴로 잘못 잡히지 않게 한다.
- S03.3 원본 요소 식별과 갱신 상태를 관리한다. DOM 교체·href 변경·경로 변경 시 후보를 무효화하고 필요한 경우 제한된 재분석을 한다. observer는 확장 자신의 DOM을 제외하고 종료 시 정리한다.
- 완료 조건: 가상 비공개 문자열이 후보·쉬운 화면·진단 로그에 나타나지 않는다. 지정된 변화 사례의 낡은 후보가 실행되지 않는다. 원본 페이지의 입력과 기존 동작을 보존한다.

### S04. 분류·순위·중복 정책

- B03의 URL 단독 규칙 지원 여부와 보수적인 채택 조건을 명시한다. 잘 모르는 기능을 억지로 분류하지 않는다.
- 목적지/액션 중복 제거와 분류별 노출 개수 정책을 분리해 B05를 해결한다. 사용자가 별개의 중요 기능에 도달할 경로를 유지한다.
- 범용 규칙과 사이트별 보정 규칙은 별도로 실행·평가한다. 보정은 외부 코드를 받아 실행하는 방식으로 구현하지 않는다.
- 완료 조건: 정답표에 대한 수정 전후 수치와 실패 사례를 남긴다. 새 점수의 의미를 확률로 설명하지 않는다. 평가용 5개 페이지에 맞춰 규칙을 임의 조정한 뒤 같은 평가를 독립 검증이라고 부르지 않는다.

### S05. 액션과 원본 복귀

2026-10-18 사용자 결정: **“일반 링크는 바로 이동 유지”**. 일반 HTTP(S) 링크 카드는 현재 href·target으로 직접 이동한다. isolated world에서는 DOM 표식 없는 property/위임 이벤트를 완전히 판별할 수 없어 원본 JS/SPA handler를 우회할 수 있다. 이 한계와 재현을 [액션 정책](ACTION_POLICY.md)에 기록한다. 모든 원본 JavaScript 경로 보존을 S05 통과로 주장하지 않는다. 명시적 JS·팝업·다운로드·인증·fragment 제어는 원본 위치 안내로 처리하며 자동 클릭하지 않는다. 사용자가 선택한 직접 이동 정책 안에서 정의 사례의 의미·현재성·복귀를 검사한다.

- 일반 URL·페이지 내 앵커·JS/위임 이벤트·SPA 링크·다운로드·새 창·이름 있는 대상 창·base target·SSO 외부 도메인을 포함한 처리 사례를 만든다.
- 원본 요소가 제거되거나 href가 바뀌면 이전 URL로 진행하지 않는다. 판단이 어려운 기능은 원본에 안내하고 사용자가 실행한다.
- 현재 사이트와 다른 목적지 도메인, 새 창 여부를 표시한다. 팝업이 원본 제어를 가리는 경우 잘못된 성공 안내를 하지 않는다.
- 완료 조건: 정의한 액션 사례 전체 통과, 의도하지 않은 제출·인증·삭제 실행 0건, 종료·초점·스크롤·임시 강조 스타일 복구 확인.

## 5. 실행·검증·중단점 규칙

- 구현 변경에는 관련 실패를 재현하는 검증을 먼저 정하고 최소 수정 후 타입 검사·관련 테스트를 실행한다. 단계 종료 시 필요한 통합 검사와 빌드를 수행한다. 이미 통과한 검사를 이유 없이 반복하지 않는다.
- 각 작업 묶음은 목표 → 관찰 → 수정 → 검증 → 진행표 갱신 → 다음 실행 가능 작업 순서로 진행한다.
- 시간/예산이 가까워지면 마지막 구간을 검증·정리·재개 기록에 남긴다. 진행 중 기능을 완료로 표시하지 않는다.
- 독립적인 코드 검토·사이트 조사·테스트 설계는 병렬로 수행할 수 있다. 같은 파일을 여러 작업자가 동시에 수정하지 않으며 검토·통합 비용도 예산에 포함한다.
- 토큰 실측이 제공되지 않으면 사용량은 `UNKNOWN`으로 둔다. 모델이 체감상 사용한 숫자를 실제 계정 소비량으로 기록하지 않는다.
- 코드 변경 이력은 로컬 Git 등 복구 가능한 방식으로 관리할 준비를 한다. 외부 저장소 생성·push·게시가 명세서 작성만으로 실행되는 것은 아니다.

다음 실행은 [PRETEST](PRETEST.md)의 실제 관찰을 별도 기록하고, S07의 새로운 미노출 평가 자료·범용 누락 개선과 [S06/S08 수동 확인](MANUAL_CHECK.md)을 병행하는 것이다. 정한 인수 조건은 그대로 유지한다. ZIP·보고서를 만들었다는 이유로 S10이나 전체 10단계를 완료로 바꾸지 않는다.
