# **09 로컬 AI 검토** — 로컬 AI·소형 분류 모델 활용 계획과 시험 결과

작성일: 2026-10-31 (10절 2026-11-15 추가) · 기준: v0.10.0 (RUN-009 마감, 5/10 · NOT_MET) · 상태: **2026-10-31 사용자 지시로 소형 분류 모델 트랙(M0~)만 재개. 2026-11-15 사용자 컴퓨터 AI 점검(10절).** 새 독립 자료 수집, 다음 버전 패키지, 제품 동작 변경은 이 재개 범위에 포함하지 않는다.

이 문서는 Mac mini에 구성된 로컬 AI(Ollama)를 EasyWeb 개선에 쓸 수 있는지 검토한 결과와 실행 계획이다. 장기 작업 일시 정지 경계([user-stop-boundary](evidence/run009/user-stop-boundary.json))는 그대로이며, 이 문서를 작성했다고 해서 다음 버전이나 새 자료 수집을 시작한 것은 아니다.

## 1. 결론

> **2026-10-31 실행 결과 반영:** 아래 표는 실행 전 판단이다. M1에서 소형 모델이 규칙 엔진보다 크게 낮았고(expected 분류 67% 대 99%), LLM 합성 데이터의 효과도 거의 없었다. 그래서 A는 **진단 도구로만 보존**하고 제품 탑재(M2)는 진행하지 않는다. 자세한 내용은 9절에 있다.
>
> **2026-11-15 사용자 컴퓨터 AI 점검 반영:** 사용자 PC에서 LLM을 실시간으로 돌리는 것은 품질·크기·속도 모두 맞지 않았다. 페이지 유형을 보고 첫 화면을 고르는 아주 작은 학습 모델(1MB·2ms)은 엔진과 섞을 때 개발 자료에서 효과가 확인됐다(37.2% → 43.6%). 10절 참조.

**가능하다. 제품 안에는 LLM 대신 작은 분류 모델(문자 n-gram + 선형 모델)을 넣는 쪽이 맞고, LLM은 필요할 때만 개발 보조로 쓴다.**

| 활용 방식 | 판단 | 이유 |
| --- | --- | --- |
| A. 소형 분류 모델 (확장 안에서 실행) | **권장, 주 경로** | 가중치를 정적 JSON으로 넣으면 권한·외부 호출·런타임 의존성이 없다. 추론이 가벼워 성능 예산 안에 들어갈 가능성이 높고, 어떤 글자 조각 때문에 그렇게 분류했는지 설명할 수 있다. 4A절 참조. |
| B. LLM 개발 보조 (오프라인 분석·반례 초안) | **선택** | 제품에 영향 없음. 실패 원인 분석, 라벨링 보조, 반례 초안에만 쓴다. |
| C. LLM 런타임 호출 | **하지 않음 (기록용 실험만)** | 재호출도 1.9초 이상이라 300ms/1초 예산과 맞지 않는다. 권한이 추가로 필요하고, 대상 사용자 PC에는 로컬 모델이 없다. |
| D. 사람 실증·접근성·독립 평가 대체 | **사용하지 않음** | S06 발화·확대, S08 설치, S09 실증은 실제 관찰만 인정한다. 모델 출력으로 대체하지 않는다. |

AI 분류는 [작업명세서](WORK_SPEC.md) 1절에서 v1.0 파일럿의 **별도 후속 범위**로 정해져 있다. 따라서 B는 v1.0 인수 조건에 포함하지 않는 탐색 과제로 둔다.

## 4A. 소형 분류 모델 검토 (LLM 대안)

"LLM까지는 과하다"는 판단에 맞춰, 로컬에서 학습하고 확장 안에서 바로 돌릴 수 있는 후보를 비교했다. 크기와 지연은 일반적인 규모를 기준으로 한 **추정치이며 이 저장소에서 측정하지 않았다.**

| 후보 | 학습 (Mac mini) | 확장 안 실행 | 예상 크기 | 장점 | 한계 | 판단 |
| --- | --- | --- | --- | --- | --- | --- |
| **문자 n-gram(1~3) + 로지스틱 회귀** | scikit-learn, 수 초 | 가중치 JSON + TS 내적 계산 수십 줄 | 수십~수백KB | 한국어 형태소 분석기 없이 동작. 의존성 0. 상위 n-gram을 `reasons`에 그대로 쓸 수 있다. | 문맥 이해가 얕고, 처음 보는 표현에 약하다. | **1순위** |
| fastText supervised | `fasttext` CLI/파이썬, 수 초 | wasm 런타임이 필요하거나 추론을 직접 구현 | 양자화해도 수MB | 서브워드 일반화가 조금 더 낫다. | 확장 크기(현재 ZIP 605KB)가 크게 늘어난다. 선형 모델과 성능 차이가 크지 않을 가능성이 높다. | 2순위 (1순위가 부족할 때만 비교) |
| 소형 한국어 인코더 파인튜닝 (KLUE-RoBERTa-small, multilingual-e5-small 등) + ONNX/transformers.js | PyTorch, M4 Pro MPS로 수십 분 | wasm/WebGPU 런타임 | 수십~100MB 이상 | 의미 일반화가 가장 좋다. | 학습 데이터가 너무 적어 장점을 살리기 어렵다. 1000개 제어 일괄 추론이 300ms를 넘길 위험이 있다. | 보류 |
| Ollama 임베딩 + 최근접 이웃 | 임베딩 모델을 추가로 받아야 함 | 런타임 불가 (Ollama 의존) | — | 개발 중 표현 군집 분석에는 유용하다. | 제품에 넣을 수 없다. | 개발 분석용만 |

### 왜 선형 모델이 맞는가

- 현재 분류기([classifier.ts](../src/classifier.ts))는 이미 "이름·섹션 정규식 + URL 끝 경로" 구조다. 선형 모델은 같은 입력에 **가중치만 학습**하는 형태라 기존 규칙과 쉽게 합쳐진다.
- 학습 자료가 작다. 개발 60페이지의 기대 기능은 약 290개이고, 나머지 fixture 제어가 음성 예시다. 이 규모에서는 큰 모델보다 규제를 건 선형 모델이 과적합을 덜 한다.
- 가중치 JSON은 동결 해시와 ZIP 재현성 검사에 그대로 포함할 수 있다.

### 모델의 역할 제한

모델은 규칙을 대체하지 않는다. "근거 없는 기능 생성 금지"와 최초 6개 기준을 지키기 위해 다음 순서로 역할을 넓힌다.

1. **진단 전용**: 규칙 분류와 모델 예측이 다른 후보를 개발 비교 보고서에 표시한다. 표시 오분류 4개 같은 문제를 찾는 데 쓴다. 제품 동작은 바뀌지 않는다.
2. **동률 정리**: 규칙 점수가 같은 후보끼리만 모델 확률로 순서를 정한다. v5 동률 탭 문제가 대상이다.
3. **보조 점수**: 규칙 근거가 있는 후보에만 상한을 둔 가산점을 준다. 모델 점수만으로 채택 기준(55)을 넘을 수 없게 한다.

각 단계는 이전 단계가 개발 자료에서 회귀 없이 통과한 뒤에만 진행한다.

### 입력 특징

- 후보의 안전한 `label`, `sectionLabel`, `contextLabels`, `context`(primary/body/footer), href의 마지막 경로 조각(쿼리 제외)
- 입력값·편집 내용·value/checked는 기존 수집 단계에서 이미 빠져 있으므로 새로 읽지 않는다.

### 학습·검증 방법

- **사이트 단위 교차 검증**(5개 사이트 중 1개씩 빼고 학습)으로 같은 사이트 정보가 새는 것을 막는다.
- holdout·새 독립 자료는 학습에도 하이퍼파라미터 선택에도 쓰지 않는다.
- 비교 기준선은 현재 규칙 엔진이다. 기관모드 286/290 정확·169/170 재현·60/60 추천보다 나빠지는 변경은 채택하지 않는다.
- 학습 데이터를 현재 규칙 출력으로 만들지 않는다. 그렇게 하면 모델이 규칙을 그대로 따라 배울 뿐이다. 정답표 라벨만 쓴다.

### 필요한 환경

- Python 3.14는 있으나 `scikit-learn`이 없다. 프로젝트 밖 가상환경(예: `~/.venvs/easyweb-ml`)에 설치하는 것을 제안하며, **설치는 사용자 확인 후** 한다. 제품 빌드 의존성(`package.json`)은 늘리지 않는다.
- 학습 스크립트는 `scripts/ml/`에, 가중치는 `src/model/`에 두고 학습 데이터 해시·seed·버전을 함께 기록한다.

### Jev(TypeSafe AI)와 비슷한 결정 모델

Jev는 문장을 생성하지 않고, 상태와 질문을 받아 선택지·점수·확률·신뢰도만 돌려주는 분류·결정 전용 모델이다(2026-09 얼리 액세스). EasyWeb의 "후보 → 분류" 문제와 형태는 잘 맞지만, 2026-10-31 웹 검색 결과로는 다음 이유 때문에 **제품에 넣거나 로컬 대안으로 쓰기 어렵다.** 공식 발표 원문을 직접 확인하지 못했고 2차 자료에 의존한 판단이다.

| 항목 | 확인 내용 | EasyWeb 영향 |
| --- | --- | --- |
| 실행 위치 | 호스팅 API 전용, 가중치 비공개, 자체 호스팅 경로 미공개 | Mac mini에서 직접 실행할 수 없다. |
| 데이터 전송 | 페이지 후보 정보를 외부 서버로 보내야 함 | "후보·로그·저장소 비수집" 원칙, 권한 최소화와 충돌한다. 확장에 외부 host 권한이 필요하다. |
| 비용 | 입력 100만 토큰당 약 0.042달러(유료) | 저렴하지만 유료 API는 사용자 지시 범위에서만 쓸 수 있다. |
| 평가 근거 | 공개 벤치마크가 아닌 회사 자체 워크플로 평가 | 한국어 기관 메뉴 성능은 알 수 없다. |

로컬 대안으로 커뮤니티 구현이 있다. 다만 모두 **Jev 자체가 아니며 성숙도·라이선스를 확인하지 않았다.**

- `jeff`: 400M 파라미터 GLiFormer 기반 System One API 호환 서버
- `selfjev-4b`: 4B 공개 결정 모델 (PyPI `selfjev`)
- `OpenJev`: 2026-09-20 첫 커밋, 라이선스 미표기

판단:

- **제품 런타임에는 쓰지 않는다.** 400M~4B 모델은 확장 안에 넣기에 너무 크다. 로컬 서버로 띄우면 LLM 런타임 호출(1절 C)과 같은 권한·배포 문제가 생긴다.
- **개발 보조로는 비교해 볼 수 있다.** M1에서 선형 모델과 함께 `jeff` 같은 로컬 결정 모델을 개발 60페이지에 돌려, 규칙·선형 모델이 놓친 표현을 찾는 2차 진단으로 쓴다. 이때도 holdout은 쓰지 않는다. 설치는 라이선스 확인과 사용자 확인 후에 한다.
- 호스팅 Jev API로 공개 fixture를 진단해 보는 것도 기술적으로는 가능하지만, 유료·외부 전송이라 사용자가 명시적으로 지시할 때만 한다.

참고: [TypeSafe AI 문서](https://docs.typesafe.ai/introduction) · [Jev 설명(CometAPI)](https://www.cometapi.com/ko/what-is-jev/) · [나무위키](https://namu.wiki/w/Jev) · [로컬 실행 검토](https://www.modemguides.com/blogs/ai-news/jev-typesafe-reality-check-run-locally) · [LangChain4j 연동](https://docs.langchain4j.dev/integrations/decision-models/typesafe) · [selfjev](https://pypi.org/project/selfjev/)

### 현실적인 기대치

데이터가 60페이지뿐이라 모델이 규칙보다 크게 나아지기는 어렵다. 가장 현실적인 효과는 **(1) 규칙이 놓친 표현을 찾아내는 진단**과 **(2) 동률 정리**다. 모델 성능을 의미 있게 키우려면 라벨된 페이지가 더 필요한데, 새 자료 수집은 일시 정지 범위 밖이므로 재개 후 별도로 결정한다.

## 4B. LLM으로 학습 데이터 만들기

가능하며, 데이터가 60페이지뿐인 현재 상황에서는 오히려 LLM의 가장 쓸모 있는 역할이다. LLM을 제품에 넣는 대신 **작은 모델의 선생(teacher)**으로 쓰는 방식이다.

| 방식 | 내용 | 주의 |
| --- | --- | --- |
| 합성 증강 | 분류별 메뉴 이름 변형 생성 (예: 공지사항 → 알림마당·새소식·보도자료, 신청 → 접수·예약·발급) | 실제 기관 표현과 분포가 다르다. 실제보다 매끄러운 말투로 치우칠 수 있다. |
| 헷갈리는 음성 예시 | 키워드는 겹치지만 분류가 아닌 이름 생성 (예: "개인정보처리방침", "공지 구독 해지", "검색 결과 0건") | 규칙 엔진의 오탐 패턴을 학습시키는 데 유용하다. |
| 약한 라벨 (증류) | 실제 fixture에서 정답 ID가 없는 제어를 LLM이 분류 → 작은 모델이 학습 | 2절 시험처럼 LLM도 틀린다. LLM 오류가 그대로 학습된다. |

규칙:

1. **검증·테스트에는 실제 사람 라벨만 쓴다.** 합성·LLM 라벨이 검증에 섞이면 점수가 부풀려지고, LLM 오류를 발견할 수 없다.
2. **효과를 따로 측정한다.** 실제만 / 실제+합성 / 실제+합성+약한 라벨을 같은 사이트 단위 교차 검증으로 비교하고, 나아질 때만 채택한다.
3. 약한 라벨은 두 모델(`qwen3:14b`, `gemma4:e2b`)이 일치한 것만 쓰고, 실제 라벨보다 낮은 가중치를 준다.
4. 합성 문장은 `synthetic` 표시와 생성 모델 digest·프롬프트·seed를 남긴다. 사이트 이름·문서 번호·URL 쿼리를 생성하지 않는다(매핑 금지).
5. holdout이나 새 독립 자료의 페이지·정답을 프롬프트에 넣지 않는다.

## 4. 계획

단계 번호는 기존 S01~S10과 구분해 **L0~L4**로 둔다. 각 단계는 완료 조건을 만족해야 끝난다. 4A절의 소형 분류 모델은 **M0~M3**로 따로 두고, L 단계보다 먼저 진행한다.

### M0. 학습 환경과 데이터 추출

- 별도 가상환경에 scikit-learn 설치 (사용자 확인 후)
- 개발 60페이지 fixture를 별도 headless로 분석해 후보 특징과 정답 라벨(6개 분류 + none)을 JSONL로 추출
- 완료 조건: 추출 결과의 후보 수·라벨 분포·사이트별 개수가 기록되고, 사적 값이 없음을 확인하는 음성 검사를 통과한다.

### M1. 기준 모델 학습과 진단 출력

- 문자 n-gram 로지스틱 회귀를 사이트 단위 교차 검증으로 학습
- 4B절의 LLM 합성·약한 라벨을 넣은 경우와 뺀 경우를 함께 비교
- 규칙과 모델의 불일치 목록을 개발 비교 보고서 옆에 별도 파일로 출력
- 완료 조건: 분류별 정밀도·재현율, 규칙 대비 차이, 불일치 사례 검토 결과가 남는다.

### M2. 확장 내 추론과 동률 정리

- 가중치 JSON과 TS 추론 함수를 추가하고, 동률 후보 순서에만 적용
- 기존 493검사 + 동률 반례 검사 + 1000제어 성능 측정(기관/범용)을 실행
- 완료 조건: 개발 비교에서 회귀 0, 기존 성능 기준 PASS, ZIP 재현성 유지

### M3. 보조 점수 (선택)

- 상한이 있는 가산점을 실험하고, 효과가 없으면 M2에서 멈춘다.
- 완료 조건: 개선·회귀 사례가 모두 기록되고 채택/기각 판단이 남는다.

### L0. 공통 도구 준비 (개발 보조 기반)

- `scripts/local-ai/` 아래에 Ollama 호출 래퍼를 둔다. Node 내장 `fetch`만 쓰고 의존성을 추가하지 않는다.
  - 고정 설정: 모델명, `temperature: 0`, `format: json`(또는 JSON schema), `think` 여부, seed
  - 기록: 모델 digest, 프롬프트 해시, 입력 해시, 출력, 지연을 `docs/evidence/local-ai/<실행ID>/`에 저장
  - 입력 필터: 후보의 `label`·`category`·`contextLabels`·`sectionLabel`·`reasons`만 허용. href는 호스트와 경로 마지막 조각까지만, 쿼리는 제거
- `npm run verify`에는 넣지 않는다. 모델 출력이 비결정적일 수 있어 회귀 검사와 섞지 않는다.
- 완료 조건: 같은 입력을 3회 실행해 출력 차이를 기록하고, 입력 필터 음성 검사(사적 값·쿼리가 들어가면 거부)를 통과한다.

### L1. 실패 원인 분석 보조 — 우선순위 1

대상: RUN-009에 남은 결함

- v5 동률 읽기 탭 1개가 첫 6개 밖으로 밀리는 문제
- 60페이지 표시 오분류 4개 (정부 소식보기의 help 분류 포함)
- 범용 모드 327.1ms 추가진단 FAIL (원인 분석만, 성능 측정은 기존 도구로 함)

방법:

1. `npm run compare:development -- --output-dir=<새 빈 경로>` 결과에서 FAIL·오분류 후보를 뽑는다.
2. 후보별로 이름·주변 제목·적용된 규칙(`reasons`)·점수를 `qwen3:14b`(필요하면 `qwen3.6:27b`)에 주고 다음을 묻는다.
   - 왜 이 분류/순위가 나왔는지 규칙 관점의 설명
   - 다른 페이지에 부작용이 적을 규칙 수정 후보 2~3개
   - 각 수정이 깨뜨릴 수 있는 반례
3. 사람이 후보를 골라 **결정적 규칙**으로 구현하고 기존 493검사 + 새 반례 검사로 확인한다.

완료 조건: 위 결함마다 모델 제안·채택/기각 사유·최종 수정과 전후 결과가 증거 파일로 남는다. 모델 제안을 채택했다는 사실만으로 PASS를 주장하지 않는다.

### L2. 반례·fixture 초안 생성 — 우선순위 2

- `qwen2.5-coder:14b`로 기존 fixture 구조를 따르는 **합성 HTML 변형**을 만든다. 예: 같은 이름의 탭이 동률일 때, 공지 링크가 help 섹션 안에 있을 때, 같은 마크업으로 행이 교체될 때.
- 생성물은 `tests/`의 합성 반례로만 쓴다. 파일명·메타데이터에 `synthetic`·생성 모델·digest를 남기고, **실제 기관 페이지나 독립 평가 자료로 세지 않는다.**
- 완료 조건: 사람이 검토한 반례가 실제 결함을 재현(수정 전 FAIL)하거나 기존 동작을 고정(수정 전후 PASS)하는지 기록된다.

### L3. 쉬운 말 문구 검토 — 우선순위 3

- 대상: `CATEGORY_INFO` 설명, 원본 위치 안내([original-notice.ts](../src/original-notice.ts)), 오류·빈 결과 안내, [INSTALL](INSTALL.md)·[MANUAL_CHECK](MANUAL_CHECK.md) 사용자용 문장.
- 모델에게 어려운 단어·긴 문장·이중 부정을 표시하게 하고 대안 문장을 받는다. 접근성 이름 길이와 스크린리더 읽기 순서를 함께 본다.
- 채택은 사람이 한다. 실제 이해도는 S09 실증에서만 판정한다.
- 완료 조건: 문구 변경 전후 표와 자동 접근성 21조건 재검사 결과가 남는다.

### L4. 런타임 보조 실험 (선택) — v1.0 범위 밖

L1~L3 이후, 사용자가 원할 때만 진행한다.

- 별도 실험 빌드(`--experimental-local-ai`)에서만 켠다. 파일럿 ZIP·Manifest는 바꾸지 않는다.
- 흐름: 규칙 엔진이 첫 화면을 먼저 그린다 → 사용자가 실험 기능을 켜 둔 경우에만 background가 안전 필드만 로컬 모델에 보낸다 → 결과가 오면 다음을 제안한다.
  - (a) **동률 후보 안에서만** 순서 보정 (첫 6개의 규칙 결정을 뒤집지 않음, 다른 메뉴 안의 순서만 조정하는 것부터 시작)
  - (b) 카드 아래 한 줄 쉬운 설명 (원본 label은 그대로 둠)
- 결과 검증: 후보 ID 집합 밖 출력, 새 기능, URL·스크립트 문자열이 있으면 버린다. stale 검사는 기존 경로를 그대로 탄다.
- 필요한 설정: `optional_host_permissions`, Ollama의 `OLLAMA_ORIGINS=chrome-extension://<확장ID>`, 2초 시간 제한, 실패 시 조용히 규칙 결과만 유지.
- 측정: 규칙 단독 대비 개발 60페이지 정확·재현·추천과 지연 분포. 독립 평가 주장은 하지 않는다.
- 완료 조건: 실험 빌드에서 개인정보 음성 검사, 권한 미부여 시 동작 불변, 모델 꺼짐/시간 초과 시 동작 불변이 확인된다.
- 실제 배포 경로를 고려하면 사용자 PC에 Ollama가 없으므로, 장기적으로는 브라우저 내장 모델(Chrome 내장 AI API 등) 검토가 별도로 필요하다. 이 문서 범위에서는 조사하지 않았다.

## 5. 평가 무결성 규칙

1. 모델에게 holdout(새 독립 자료)의 페이지·정답·URL을 보여주지 않는다.
2. 모델 제안으로 고친 규칙의 개선은 "개발 자료 결과"로만 보고한다. 과거 첫 FAIL(v10 26/28·2/15·0/5 등)은 그대로 둔다.
3. 모델 출력으로 정답표·주석을 직접 수정하지 않는다. 주석 의심 사항은 기존 방식처럼 별도 감사 파일에 남긴다.
4. 모델 digest·프롬프트·출력을 증거로 남긴다. 같은 결과를 재현할 수 없으면 그 사실도 기록한다.

## 9. M0·M1 실행 결과 (2026-10-31)

사용자 지시로 M0·M1과 4B 합성 데이터 시험까지 실행했다. 제품 코드(`src/`)와 Manifest는 바꾸지 않았다. 모든 수치는 **노출된 개발 60페이지** 결과이며 독립 평가가 아니다.

### 실행 내용

- 환경: `~/.venvs/easyweb-ml` (scikit-learn 1.9.1, numpy 2.5.4). 프로젝트 의존성은 그대로다.
- [M0 추출](evidence/local-ai/m0/summary.json): [extract-dataset.mjs](../scripts/ml/extract-dataset.mjs)가 개발 비교와 같은 고유 10 suite·60페이지를 별도 headless로 분석했다. 후보 962개 중 954개에 사람 라벨이 있다(`accepted` 분류, 검토했지만 허용하지 않은 제어는 none). `expected` 189개. href는 마지막 경로 조각만 쓰고 쿼리는 0건이다.
- [M1 학습](../scripts/ml/train.py): 문자 n-gram(이름·주변 제목·경로) + 제어 메타데이터, 로지스틱 회귀, 5개 기관 사이트 단위 교차 검증.
- [4B 합성](evidence/local-ai/synthetic-qwen3-14b/summary.json): [synthesize.py](../scripts/ml/synthesize.py)가 `qwen3:14b`에 분류 정의와 기관 유형만 주고 이름 280개(중복 제거)를 만들었다. 개발 데이터는 프롬프트에 넣지 않았다. 학습 fold에만 가중치 0.3으로 넣었다.

### 라벨 해석 주의

`accepted`는 "보여줘도 되는 분류" 목록이다. 규칙이 accepted 제어를 추천하지 않은 것은 오류가 아니다. 그래서 전체 라벨 정확도(규칙 75%)가 아니라 **양쪽이 실제로 분류를 주장한 항목**으로 비교했다.

### 결과

| 지표 | 규칙 엔진 | 모델 (실제 데이터만) | 모델 (+LLM 합성) |
| --- | ---: | ---: | ---: |
| 규칙이 분류를 붙인 435개의 정확도 | **97.0%** | 59.8% | 60.7% |
| expected 189개의 분류 정확도 | **98.9%** | 67.2% | 67.7% |
| 사이트별 expected (상명대 / 천안시) | — | 35.1% / 61.9% | 40.5% / 52.4% |
| 규칙 오류 13개 중 모델이 맞힌 수 | — | 3 (확신도 0.45~0.56) | 2 |

규칙 점수는 같은 60페이지에 맞춰 개발됐으므로 낙관적인 값이다. 그래도 차이가 커서 결론은 바뀌지 않는다. [실제만](evidence/local-ai/m1-real/report.json) · [합성 포함](evidence/local-ai/m1-synthetic/report.json)

### 원인

1. **정답이 이름보다 구조에 달려 있다.** 상명대 expected의 "pdf 다운로드"(장학금 규정 표 안)와 "천안캠퍼스"는 academic이다. "검색어를 입력해 주세요"는 search다. 이 판단은 규칙 엔진의 표·섹션·관계 모듈이 담당하는데, 이름 중심의 선형 모델은 사이트 5개 분량의 데이터로 이 관계를 배우지 못한다.
2. **분류 경계가 이 프로젝트의 주석 관례다.** "민원 신청안내"·"자료상담·신청"은 help, "센터소식 선택됨"은 notice다. 모델도 LLM도 이 관례를 모른다. 규칙 오류 13개 중 다수가 이 경계에 있다.
3. **사이트 유형이 치우쳐 있다.** academic은 대부분 상명대에만 있다. 상명대를 빼고 학습하면 academic을 거의 배우지 못한다.
4. **LLM 합성 데이터는 잡음이 컸다.** "장학금 신청"·"공고사항"·"행사일정"을 none으로 만드는 등 분류 정의를 어겼고, "○○ 신청/조회/내역"처럼 반복이 많았다. 일부 사이트는 좋아지고 일부는 나빠져서 합계 효과는 거의 0이었다.

### 판단

- **M2(확장에 넣어 동률 정리)는 진행하지 않는다.** 규칙과 의견이 다를 때 모델이 맞을 근거가 없다. 규칙 오류에서도 확신도가 낮다.
- M0 추출기와 M1 학습기는 **진단 도구로만 보존**한다. `report.json`의 `ruleErrors` 13개는 표시 오분류 검토 목록으로 쓸 수 있다. 정부 소식보기 help 오분류("센터소식 선택됨")도 여기에 포함되어 있다.
- 소형 모델이 의미 있어지려면 이름이 아니라 **구조 특징**(표 열 제목, 섹션 역할, 반복 목록 위치)을 넣어야 하고, 라벨된 사이트도 훨씬 많아야 한다. 새 자료 수집은 이번 재개 범위 밖이므로 사용자가 별도로 결정한다.
- LLM 합성을 다시 시도한다면 두 모델 일치 필터, 분류 정의에 이 프로젝트의 경계 사례 포함, 실제 구조 문맥 부여가 필요하다. 다만 원인 1·2가 해결되지 않으면 효과는 제한적일 것으로 본다.

## 10. 사용자 컴퓨터에서 돌리는 AI 점검 (2026-11-15)

사용자 질문: "사용자 컴퓨터의 GPU나 메모리로 가벼운 AI를 돌릴 수 있지 않나?" → 사용자 지시로 **가용 성능과 성능 대비 효과만 점검**했다. 제품 코드(`src/`)·Manifest·`package.json`은 바꾸지 않았다. D8(제품에 넣지 않음)은 그대로다.

### 무엇을 시험했나

- 과제: 2026-11-01 사이트 조사 134페이지에서 **첫 화면 카드 6개 고르기**. 기준은 엔진을 보지 않은 Claude 검토자의 필수 기능([보고서](reviews/site_survey_20261101.md))이고, 채점은 같은 방식(필수 기능이 카드나 자주 쓰는 버튼 줄에 있으면 포함)이다. 지금 엔진은 37.2%.
- 비교 방식 3가지: 모델이 혼자 고름(alone) · **섞음**(게시판·게시글·관문은 지금 엔진, 나머지 페이지만 모델) · 홈만 모델.
- 개선폭은 사이트 23개 단위로 2,000번 다시 뽑은 95% 구간으로 봤다. 구간이 0을 넘어야 우연이 아니라고 본다.
- 모델 입력은 조사 때 모은 고정 이름·영역·가까운 제목·짧은 경로뿐이다. 입력값은 애초에 수집하지 않았다.
- 도구: [ondevice-llm.mjs](../scripts/ml/ondevice-llm.mjs) · [ondevice-rank.py](../scripts/ml/ondevice-rank.py) · [ondevice-embed.mjs](../scripts/ml/ondevice-embed.mjs) · [ondevice-browser.mjs](../scripts/ml/ondevice-browser.mjs) · [ondevice-score.mjs](../scripts/ml/ondevice-score.mjs). 결과: [evidence/run010/local-ai-ondevice-20261115](evidence/run010/local-ai-ondevice-20261115/score.json)

### 결과

| 방식 | 크기 | 한 페이지 시간 | 혼자 | 섞음 | 섞음 개선폭 (95% 구간) |
| :---- | ---: | ---: | ---: | ---: | :---- |
| 지금 엔진 | — | 수십 ms | — | **37.2%** | — |

| 위 + 문장 임베딩(e5-small) | +118MB | 브라우저 0.9~9.7초 | 39.1% | 45.1% | +4.3 ~ +11.7%p |

- 시간은 모두 **개발용 Mac(M4 Pro, 24GB)** 기준 중앙값이다. 대상 사용자 PC는 이보다 느리다.

- 홈만 모델로 바꾸면 효과가 작다(문자 조각 +0.9%p, 12b +3.2%p). 효과의 대부분은 **오시는 길·안내·서비스처럼 지금 엔진이 기본 규칙만 쓰는 페이지**에서 나온다.
- 브라우저 임베딩: 별도 headless Chromium에서 모델 로딩 0.6~0.9초, 페이지당 1스레드 3.4~9.7초, 4스레드 0.9~3.4초. headless WebGPU는 20~55초로 GPU를 실제로 쓰지 못한 것으로 보여 판단에 쓰지 않는다.

### Chrome 내장 AI (Gemini Nano)

- **이 컴퓨터에서 시험하지 못했다.** 빈 공간이 7.6GB인데 22GB 이상이 필요하다. 그 밖에 GPU 메모리 4GB 초과 또는 RAM 16GB·4코어 이상, 처음 한 번 모델 내려받기가 필요하다.
- 공식 지원 언어는 영어·일본어·스페인어·독일어·프랑스어이고 **한국어는 목록에 없다** (2026-11-15 Chrome 문서 확인).
- 같은 계열 소형 모델(gemma4:e2b)의 결과가 엔진보다 낮아서, 한국어 지원이 생겨도 이 과제에서 품질이 오른다는 근거는 아직 없다.

### 해석과 한계

- **기준이 Claude 검토라서 LLM에게 유리할 수 있다.** 큰 LLM의 높은 점수는 "Claude와 비슷하게 고른다"는 뜻일 수 있고, 할머니·어머니가 실제로 원하는 것과 같다는 근거는 아니다.
- 반대로 지금 엔진은 이 134페이지를 보며 다듬었으므로 엔진 점수는 낙관적이다. 학습 모델은 자기 사이트를 보지 않고 채점했다.
- 표본은 23개 사이트 134페이지뿐이다. 페이지 유형별 수치는 페이지 수가 적어 흔들림이 크다.
- 임베딩 원본 벡터(약 30MB)는 저장하지 않았다. `ondevice-embed.mjs`로 다시 만들 수 있다.
- gemma4:12b는 한 페이지가 300초 넘게 걸려 실행이 멈췄다. 123페이지는 기록에서 되살리고([partial](evidence/run010/local-ai-ondevice-20261115/llm-gemma4-12b-partial.json)) 나머지를 이어서 돌렸다.
- 첫 LLM 일괄 실행에서는 이름에 `|`가 들어간 67줄(0.4%)이 칸이 밀린 채 입력됐다. 번호는 맞아서 채점에는 영향이 없다.

### 판단

1. **사용자 컴퓨터에서 LLM을 실시간으로 돌리는 것은 지금 맞지 않다.** 사용자 PC에서 돌 만한 크기(e2b)는 품질이 엔진보다 낮다. 품질이 좋은 크기(12b)는 7.7GB이고, 고사양 Mac GPU에서도 13초가 걸린다.
2. **가장 효과 대비 비용이 좋은 것은 아주 작은 학습 모델(문자 조각 + 선형)이다.** 1MB·2ms로 성능 기준 안에 들어가고, 섞음 방식에서 +6.4%p가 우연이 아니다. 임베딩을 더하면 크기는 118배, 시간은 수백 배인데 추가 효과는 확실하지 않다.
3. **큰 LLM은 사용자 컴퓨터가 아니라 개발할 때 "선생님"으로 쓰는 쪽이 맞다.** gemma4:12b가 가장 잘 골랐으므로, 개발 컴퓨터에서 많은 사이트에 라벨을 붙이고 그것으로 작은 모델을 학습시키는 방법(지식 증류)이 다음 후보다.
4. 제품에 넣으려면 먼저 해야 할 것:
   - 새 사이트에서 독립 검증. 이 134페이지는 개발 자료다.
   - 사람 관찰로 기준 확인 (03 U1/U2).
   - 모델은 이미 찾은 후보 안에서만 순서를 바꾸고, 게시판·게시글·관문과 위험·stale 차단은 규칙이 계속 정한다.
   - 이 셋은 새 자료 수집과 제품 변경이라 사용자 결정 사항이다 (07 D14).

## 12. 순위 학습과 작은 리랭커 학습 (2026-11-18)

- 목적: "엔진이 찾은 버튼 중 무엇이 가장 중요한가"를 순위로 직접 학습합니다. 학습 없는 리랭커 2종은 개발 134쪽에서 엔진보다 낮았습니다(34.3%·35.7%, 엔진 37.2%).
- 방식:
  - **순위 학습:** 1MB 모델과 같은 특징을 LightGBM LambdaRank로 학습합니다. 쪽 단위로 묶고, 필수 2점·유용 1점입니다([ondevice-rank.py](../scripts/ml/ondevice-rank.py) `--algo=lambdarank`).
  - **리랭커 조정 학습:** 다국어 MiniLM 리랭커(약 1.2억)를 검토 자료로 2회 학습했습니다([ondevice-crossenc.py](../scripts/ml/ondevice-crossenc.py)).
  - 학습 도구는 프로젝트 밖 `~/.venvs/easyweb-ml`에 설치했고, 제품 의존성은 바꾸지 않았습니다.
- 순서: 개발 134쪽 교차 검증 → 89쪽 계획 고정([plan.json](evidence/run010/ltr-20261118/plan.json)) → 89쪽 선택 저장·해시 → 한 번 채점([test-score-first.json](evidence/run010/ltr-20261118/test-score-first.json), [test-gate-first.json](evidence/run010/ltr-20261118/test-gate-first.json)).
  - 89쪽은 11-17에 다른 방식 평가에 이미 썼으므로, 이번이 같은 자료의 두 번째 사용입니다.

| 방식 | 개발 134쪽 (섞음) | 처음 보는 89쪽 (섞음) | 89쪽 호출 조건 적용 | 한 쪽 시간 |
| :---- | ---: | ---: | ---: | :---- |
| 지금 엔진 | 37.2% | 41.4% | 41.4% | — |
| 1MB 로지스틱 (기존) | 43.6% | 48.2% (+2.2 ~ +13.2) | 47.5% | 2ms |
| **순위 학습 (LambdaRank)** | **47.3%** (+5.8 ~ +14.8) | **53.2%** (+6.3 ~ +18.6) | **52.0%** (+5.6 ~ +16.1) | 약 4ms |
